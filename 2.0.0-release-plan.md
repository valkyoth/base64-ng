# base64-ng 2.0.0 Commit Release Plan

This document converts the 2.0 architecture review into ordered, reviewable
commits. The project does not publish intermediate crate versions from this
plan. Each numbered checkpoint is committed and locally verified before work
starts on the next checkpoint. External pentests may cover one checkpoint or
a contiguous batch of checkpoints at maintainer-selected intervals. Every
checkpoint must be covered and accepted before the final release. The only
release tag created by this plan is the final signed `v2.0.0` tag.

This is the authoritative executable roadmap for 2.0. The supporting
[2.0 governance decision](docs/2.0_GOVERNANCE.md) freezes how scope,
checkpoint acceptance, evidence retention, RFC terminology, and source
material are interpreted. Historical plans, architecture reviews, gap
analyses, and comparison notes remain source material rather than parallel
roadmaps. Architecture reviews and gap analyses are source material, not
executable checkpoints.

Nothing listed here is deferred beyond 2.0.0. Every implementation remains in
the 2.0 scope. Required
specifications and security proofs for portable public behavior remain release
blocking. Optional hardware backends whose native evidence is unavailable must
still ship as complete, isolated implementations, but remain unreachable from
safe automatic dispatch. The release-facing backend verification table records
implementation, project execution evidence, dispatch admission, and
independent verification separately; QEMU or compile evidence never becomes a
native-hardware claim by implication.

## Final Capability And Feature Graph

Cargo features remain additive. The 2.0 design therefore uses this fixed
capability model:

- Ordinary core: default/no-default features; portable; explicitly named strict
  RFC 4648 scalar behavior with optional ordinary SIMD.
- `simd`: additive on supported targets; ordinary encode/decode acceleration
  only. Under `std`, runtime detection selects only admitted hardware. Under
  `no_std`, acceleration requires compiler-proven `target_feature` support or
  an explicitly unsafe deployment/caller attestation whose preconditions are
  reviewed in Commit 24; otherwise execution remains scalar.
- `secrets`: additive and broadly portable; compatible with ordinary SIMD but
  implemented through structurally separate scalar secret types and
  best-effort cleanup.
- `checked-backend`: additive on supported targets and compatible with SIMD;
  enables redundant ordinary backend verification/evidence.
- High assurance: an attested build/runtime policy, not a Cargo feature. Its
  `AssuranceContext` enforces algorithm, barrier, and speculation posture and
  rejects SIMD under the required policy. Protected-memory proof remains tied
  to each exact allocation.

The final manifest edges are exact: `std -> alloc`, `stream -> std`,
`checked-backend -> simd`, and `secrets` has no implicit `alloc` edge. A
no-default-features secret array/state remains allocator-free.

`cargo test --all-features` must succeed. The explicit
`base64_ng_require_high_assurance` build policy may intentionally reject a
build that also enables `simd`, but Cargo feature unification alone never
selects high assurance. Enabling `secrets` cannot add `Drop`, wiping, staging,
or other overhead to ordinary state types.

## Final Package Topology

Every published Rust package below uses the workspace MSRV, lockstep `2.0.0`
version, repository unsafe-code policy, and shared sealed consumer traits.
Protocol companions keep parser complexity outside the zero-dependency core.

- `base64-ng`: `no_std`, zero runtime dependencies, optional `alloc`/`std`,
  incremental operation, and a capability-gated scalar secret core.
- Existing derive/serde/bytes/tokio/subtle/sanitization companions: documented
  integration-specific requirements, no hidden core dependency growth, and
  explicit capability-gated secret behavior only.
- `base64-ng-mime`: `no_std + alloc`, optional `std` I/O, incremental, core
  dependency only, and no secret surface.
- `base64-ng-pem`: `no_std + alloc`, optional `std` I/O, incremental, core
  dependency only, and bounded frame integration behind `secrets`.
- `base64-ng-multibase`: `no_std`, optional `alloc` and `std` conveniences,
  incremental, core dependency only, and no secret surface.
- `base64-ng-imap`: `no_std`, optional `alloc` conveniences, incremental, core
  dependency only, and no secret surface.
- `base64-ng-password`: `no_std`, optional `alloc`, bounded grammar/field transforms,
  no hash implementation, and no password or secret input.
- `base64-ng-openpgp`: `no_std + alloc`, optional `std` I/O, incremental, core
  dependency only, and bounded frame integration behind `secrets`.
- `base64-ng-wasm-loader`: supported JavaScript/npm loader plus scalar/SIMD
  WASM artifacts for ordinary codecs.

All new protocol companions deny unsafe code. Any additional dependency needs
its own review, exact version pin/range policy, license/advisory evidence, and
accepted pentest before Commit 54.

## Gap Analysis Disposition

The 2026-07-22 gap review is incorporated into this executable plan. In
particular, the revised checkpoints now require:

- capability-specific rollback and committed-prefix contracts instead of one
  impossible universal atomicity promise;
- bounded secret frames before plaintext release to public or irreversible
  destinations;
- production backend known-answer tests, quarantine generations, scalar retry
  policy, and high-assurance fail-closed behavior;
- separate best-effort `secrets` capability and attested high-assurance policy;
- explicit const transforms, bounded stack buffers, allocating helpers, and
  validation APIs;
- crate-owned fixed scans for custom secret alphabets;
- extensible public enums, one sealed consumer trait, and independent test
  oracles;
- artifact-level WASM selection and OS/ABI-aware RVV and SVE admission;
- exact protocol versions, scope names, parser resource budgets, and
  independent grammar models; and
- code-size, stack, allocation, pending-memory, and no-secret-reallocation
  evidence in addition to throughput.

The follow-up gap review is also resolved here: Cargo feature unification,
formatter partial writes, secret in-place behavior, exact frame storage,
password-format scope, backend self-test mechanics, assurance generations,
WASM loader ownership, sanitization prevalidation, SIMD proof boundaries,
legacy whitespace, source indexing, companion topology, and async exposure are
all assigned explicit requirements below.

The second follow-up review is resolved as well: staged secret in-place timing,
allocation-specific protection, fast-versus-checked backend writes, panic-free
safe APIs, checked source indexes, content-independent secret progress, stable
stack-limit enforcement, exact feature edges, the JavaScript/WASM contract,
zero-dependency RVV/SVE detection, writer side effects, tail wiping, token
traits, feature-size isolation, and password-record formatting are now explicit.

The third follow-up review fixes the boundary of those claims: secret timing is
fixed-work through the result gate but not through success-only declassification,
panic freedom covers crate-originated behavior rather than hostile callbacks,
memory protection is modeled at logical-allocation and effective-page levels,
and unsafe initialization, JavaScript shared-memory behavior, backend startup,
secret frame ownership, and ordinary-type ABI/auto-trait isolation have exact
checkpoint requirements.

The fourth follow-up review closes the remaining integration ambiguity:
private secret staging is always byte-disjoint from caller-visible storage,
every JavaScript entry point rejects unstable or shared backing storage, and a
versioned cross-crate semantic corpus prevents the core, streaming, Tokio,
bytes, serde, and sanitization surfaces from drifting apart.

The fifth follow-up review makes those rules capability-accurate: corpus
success is byte-identical while failure mutation follows each surface's
declared atomic/rollback/prefix contract, protected-fill is strictly
out-of-place, preflight alias/range failures are non-destructive, and WASM uses
intrinsic typed-array brand/backing checks rather than realm-local
`instanceof` or spoofable properties.

The sixth follow-up review keeps those contracts implementable: genuine
cross-realm `Uint8Array` subclasses are admitted but can be read only through
captured intrinsics, and protected decoding gains a single-allocation typestate
path that validates in place without exposing unvalidated bytes or copying
plaintext to a second protected allocation.

The seventh follow-up review freezes lifecycle and trait boundaries: cleanup
cannot survive deliberate destructor suppression or process termination,
protected-state auto traits are explicit and provider-gated, the direct path is
described as single-allocation rather than zero-copy, and the WASM loader has a
closed callback-free/species-free intrinsic allowlist.

The eighth follow-up review makes the protected cleanup lifecycle atomic and
implementable on the selected MSRV: successful direct finalization has an
explicit RAII-guard handoff with exactly one cleanup owner, conditional `Send`
is provider-proven rather than unconditionally available, and unwind auto
traits are documented as API friction rather than a security boundary.

The ninth follow-up review distinguishes exclusive cleanup ownership from
successful physical teardown. Protected values gain an ordered, fallible
teardown state machine, a reporting consuming close operation, a non-reporting
`Drop` fallback, conservative shared-page accounting, and an explicit
provider-quarantine outcome when cleanup cannot complete.

The tenth follow-up review bounds that quarantine lifecycle. Every provider
admits protected allocations against finite count, logical-byte, effective-page,
registry, and retry-work budgets; reserves an allocation-free quarantine slot
before plaintext exists; and fails closed when provider health or capacity
cannot support another allocation.

The eleventh follow-up review makes wiping a mandatory confidentiality gate in
that lifecycle. Unlock, unprotect, dump re-enablement, disposal, deallocation,
and reuse are unreachable until a complete logical-allocation wipe is verified;
any failed or indeterminate wipe transitions directly to charged, non-reusable
quarantine.

The twelfth follow-up review bounds the meaning of verification and protection:
wipe completion is an operational logical-range result with best-effort or
attested posture, not proof of erasing historical/system copies, while
conservative resource accounting remains distinct from an honest
`ProtectionUnknown` physical state.

The thirteenth follow-up review revalidates those two boundaries and makes
their implementation contract directly auditable. Commit 22 now contains one
canonical state matrix: wipe evidence, physical OS protection, and conservative
resource accounting are independent axes; no state name or accounting charge
may imply a stronger posture on either of the other axes.

The fourteenth follow-up review separates confidentiality evidence from
ownership progression. Quarantine and permanent quarantine are lifecycle
outcomes carrying the exact pending teardown stage, not wipe results. A later
unlock, accounting, or disposal failure therefore preserves valid wipe evidence
while still transferring exclusive ownership to bounded quarantine.

The fifteenth follow-up review makes retry behavior exact below that stage
boundary. Every teardown sub-operation is idempotent, conclusively atomic, or
recorded in a generation-tagged monotonic journal; ambiguous disposal becomes a
terminal non-dereferenceable tombstone instead of a retryable allocation owner.

The sixteenth follow-up review bounds that journal to its actual durability.
The default journal is preallocated volatile state for one live process and
provider-instance generation. Write-ahead means ordering before a side effect,
not persistence across termination; any persistent-recovery provider requires
its own separately admitted storage, corruption, replay, and metadata protocol.

The seventeenth follow-up review incorporates the retained comparison against
`base64` `0.23.0` and `base64ct` `1.8.3`. The 2.0 scope now explicitly includes
heapless incremental `no_std` state machines, runtime-created validated
alphabets and codec values, opt-in padding/trailing-bit compatibility policy,
named PBKDF2-adapted/BinHex/IMAP alphabet surfaces, lazy formatting and append
helpers, constant-time-oriented secret encoding, and static `no_std` SIMD under
an explicit ISA contract. Existing Commit 46 and Commit 47 requirements retain
the exact IMAP modified-UTF-7 and SHA-crypt/Passlib transforms instead of
misrepresenting them as ordinary RFC 4648 alphabets.

The eighteenth follow-up review makes the existing RFC 4648 strict posture
auditable from primary source. Commit 4 locks the exact unmodified RFC Editor
text and reviewed errata snapshot in the repository, maps its normative
requirements to code and tests, verifies the source offline in CI, and excludes
the reference text from published packages. Commits 6 and 9-12 expose strict
Standard and URL-safe padded/unpadded codecs by name while retaining strict
RFC 4648 behavior as the ordinary default.

## Commit And Pentest Protocol

Every planned commit uses the exact subject prefix shown below, for example:

```text
Commit 1: Freeze the 2.0 scope and evidence contract
```

The workflow for every numbered commit is:

1. Start from the previous development-complete checkpoint.
2. Implement only the stated goal and deliverables.
3. Run the commit-specific verification plus `scripts/checks.sh`.
4. Commit with the exact numbered subject.
5. Record the checkpoint as development-complete after local verification.
6. When the maintainer requests a pentest batch, give the pentester the
   contiguous range from the commit after the last externally covered hash
   through the selected `HEAD`.
7. Do not describe a checkpoint as release-accepted until an external PASS
   covers it. Development may continue across locally verified checkpoints
   before that batch PASS.

If a pentest finds an issue, remediation commits use the same number with a
letter suffix, such as `Commit 12a: Address incremental decode pentest
findings`. Retest the complete affected range from the last externally covered
commit through the remediation `HEAD`. Do not rewrite a pushed or reviewed
commit.

Each checkpoint must leave the repository buildable and the public security
claims honest. The checkpoint-specific pentest bullet in each exit-criteria
section identifies required review scope; a single batch report may satisfy
those bullets for every checkpoint in its covered range. Root `PENTEST.md`
remains temporary scratch input and is deleted after findings are resolved.
Intermediate batches do not create permanent GitHub pentest reports. Commit 55
adds the normalized final 2.0.0 report, records every covered checkpoint hash,
and records the final clean retest.

## Global Invariants

These requirements apply to every commit:

- The core crate remains zero-runtime-dependency and `no_std`-first.
- The workspace MSRV remains Rust `1.90.0` through 2.0.0. Newer release
  compilers and architecture evidence do not silently raise or lower that
  floor.
- Strict RFC 4648 encoding and decoding remains the ordinary default and is
  also available through explicit named strict presets. It accepts only the
  configured alphabet and padding policy, rejects non-alphabet whitespace,
  mixed alphabets, malformed or forbidden padding, non-zero unused trailing
  bits, impossible lengths, and trailing data, and emits canonical output.
- Forgiving, legacy, wrapped, and protocol-specific behavior is explicitly
  named and cannot become the default accidentally.
- Secret APIs use only constant-time-oriented scalar algorithms and mandatory
  cleanup behavior. Ordinary SIMD APIs never masquerade as secret APIs.
- Unsupported backends fall back safely. Backend faults are never reported as
  attacker-controlled malformed input.
- Safe `no_std` code cannot claim or select an ISA that the compiler target
  does not guarantee. Caller-attested static SIMD is an explicit unsafe
  contract, and its failure mode may include an illegal instruction.
- Each API follows its capability-specific commit contract. Atomic rollback is
  promised only where the crate controls rewindable storage; irreversible
  formatters, writers, async sinks, incremental output, and in-place buffers
  report committed progress or a documented post-error state.
- OOM abort, `panic=abort`, process termination, caller-owned borrowed input,
  previously accepted sink output, historical allocator copies, registers,
  caches, swap, and snapshots are outside rollback and cleanup guarantees
  unless a narrower API explicitly proves otherwise. Safe deliberate leaks via
  `mem::forget`, `ManuallyDrop`, `Box::leak`, or ownership cycles can suppress
  destruction; no secret type promises wiping when its destructor does not run.
  Forced thread termination, foreign `longjmp` across Rust frames, runtime
  abort, power loss, and process crash likewise provide no ordinary cleanup or
  journal-recovery guarantee.
- The default teardown journal is preallocated, volatile, in-process provider
  state. “Write-ahead” defines ordering relative to provider side effects only;
  it does not promise durable storage. Process termination or provider-instance
  generation termination invalidates every cursor, operation identity, and
  recovery capability. A later process or provider instance starts fresh and
  cannot interpret old volatile state as recovery evidence.
- Base 2.0 ships no persistent teardown provider unless one is explicitly named
  in the package topology. The unsafe extension protocol alone constitutes
  neither a persistent-recovery claim nor a stable persistent-provider API.
- While allocation existence is conclusive, every reachable protected-storage
  state has exactly one cleanup owner. If consuming close or destruction runs,
  that owner performs only sub-operations proven not yet applied. This is not a
  promise that every platform teardown step succeeds. Deliberate destructor
  suppression, abort, OOM abort, and process termination remain excluded;
  failed teardown leaves ownership with an explicit provider-managed quarantine
  state rather than fabricating successful wipe, unlock, accounting, or
  disposal. If disposal makes allocation existence genuinely indeterminate,
  all pointer capability is destroyed and one terminal tombstone owns only the
  accounting identity and redacted diagnostic state, never the possibly freed
  allocation.
- Protected providers have finite, checked budgets covering active, reserved,
  quarantined, and tombstoned identities together. Admission fails before
  plaintext materialization when count, logical-byte, effective-page, registry,
  or quarantine capacity is unavailable. Cleanup failure cannot cause unbounded
  resident memory, locked pages, registry growth, or retry work.
- Operationally verified completion of a full logical-allocation wipe at the
  posture required by the active policy is a prerequisite for unlock,
  protection removal, dump re-enablement, disposal, deallocation, or reuse.
  Failed, partial, interrupted, indeterminate, stale-generation, or
  insufficient-posture wiping requests no protection reduction, remains fully
  charged in conservative accounting, and transfers directly to bounded
  quarantine. Its physical OS protection is reported separately and may be
  `ProtectionUnknown`.
- Unsafe code remains isolated, inventoried, assembly-reviewed, and covered by
  architecture-specific evidence.
- All workspace crates use lockstep versions at the final release.
- Every new externally sourced protocol behavior is tied to a primary
  specification, exact vectors, and a documented scope boundary.
- Normative source copies are exact, checksum-locked, line-ending protected,
  verified without network access, tracked separately from errata and project
  interpretation, and excluded from crates.io/npm artifacts.
- Every protocol parser has caller-selectable limits for applicable input,
  output, line, label, header, skipped-byte, block/document, nesting, and
  pre-output work dimensions; defaults are finite and documented.
- No numbered commit is release-accepted without external pentest coverage and
  a PASS. Locally verified checkpoints may remain pentest-pending while later
  numbered development proceeds.
- No safe crate implementation originates a panic from malformed input,
  representable exhaustion, arithmetic/index overflow, legal state
  transitions, or resource-limit violations. Panics are limited to documented
  programmer errors and deliberate const-evaluation failures. Panics from
  caller-provided trait implementations or unsafe providers may propagate;
  crate-owned secret state is cleaned during unwinding where supported.

**Canonical teardown state model**

The implementation, reports, tests, and external review use these four
independent axes. A transition on one axis never upgrades another implicitly.

| Axis | State | Meaning and permitted consequence |
|---|---|---|
| Wipe evidence | `WipeNotCompleted` | No policy-usable complete overwrite-and-barrier result exists for the current generation; lifecycle must remain at or return to a pending wipe before any later teardown hook. |
| Wipe evidence | `WipedBestEffort` | The selected full-range overwrite and required best-effort barrier completed for the current generation; only best-effort policy may use this result. |
| Wipe evidence | `WipedAttested` | `WipedBestEffort` completed and live evidence binds the exact primitive, barrier, compiler/target/provider, and generation; high-assurance policy may use it only while that evidence remains current. |
| Physical OS protection | `ProtectionAttested` | Current provider and OS evidence confirms the declared lock/dump-exclusion posture for the exact effective pages and generation. |
| Physical OS protection | `ProtectionConfirmedAbsent` | A conclusive provider/OS result confirms that the declared protection is absent; this is never a successful high-assurance posture. |
| Physical OS protection | `ProtectionUnknown` | Query, transition, generation, or provider evidence is indeterminate; high-assurance admission and new derived capabilities are blocked until re-establishment or re-query and fresh attestation succeed. |
| Resource accounting | `Charged` | The complete allocation and effective pages count against every applicable finite provider budget, regardless of known physical protection. |
| Resource accounting | `Reconciled` | Charges may be removed only after the policy-required wipe, conclusive provider transitions, and disposal/deallocation rules all succeed. |
| Lifecycle/ownership | `Live` | The public protected value has the sole cleanup owner and no teardown attempt has consumed it. |
| Lifecycle/ownership | `Closing { stage }` | A consuming close or `Drop` owns the allocation and is executing exactly one of `Wipe`, `ProtectionRemoval`, `AccountingReconciliation`, or `Disposal`. |
| Lifecycle/ownership | `Quarantined { pending_stage }` | The provider quarantine exclusively owns an incomplete teardown and records the earliest stage whose prerequisites must be revalidated or performed. |
| Lifecycle/ownership | `PermanentlyQuarantined { pending_stage }` | Bounded recovery is exhausted; the provider retains exclusive ownership and forbids in-process reuse or deallocation until process teardown. |
| Lifecycle/ownership | `Tombstoned { last_stage, disposition }` | Allocation existence became indeterminate during disposal; no pointer or allocation ownership is retained, the provider is shut down, and only conservative accounting identity plus redacted diagnostics remain. |
| Lifecycle/ownership | `Closed` | Policy-required wipe evidence is current, protection transition is conclusive, accounting is reconciled, disposal is complete, and no allocation capability remains. |

`CleanupReport` and runtime posture snapshots report the redacted wipe and
physical-protection states separately from aggregate accounting and lifecycle
with its pending stage. In particular, `Charged + ProtectionUnknown` means only
that reuse is conservatively denied; it does not claim that pages remain locked
or dump-excluded. `Quarantined` and `PermanentlyQuarantined` identify ownership
and incomplete progress without weakening or upgrading retained wipe evidence.
Wipe completion is limited to the selected logical-range overwrite and barrier
procedure and does not claim eradication of registers, caches, swap, allocator
history, snapshots, compiler-created copies, or prior plaintext copies.

Within `Closing` or retryable `Quarantined`, a bounded `TeardownCursor` records
the exact monotonic substage and operation disposition. Journal transitions are
atomic with the provider operation or use a write-ahead provider identity that
supports conclusive reconciliation or idempotent replay; recording `Applied`
after an otherwise untracked side effect is insufficient. Recovery executes
`NotApplied` work and skips `Applied` work permanently. `Indeterminate` work may
be replayed only when the admitted idempotency proof covers that exact target
and generation; otherwise provider-specific reconciliation must classify it
first. Indeterminate disposal has no replay path: it transitions to
`Tombstoned` and destroys addressability.

For the default provider, this cursor and journal exist only in volatile memory
inside one live provider-instance generation. Write-ahead is a happens-before
contract within that lifetime, not a disk flush or crash-consistency claim.
Process termination, power loss, runtime abort, forced thread termination, or
provider-instance replacement invalidates recovery identity. Tests and reports
must not describe a normal restart as resuming teardown. A provider that claims
persistent recovery is a distinct admitted protocol and must satisfy the
durability requirements above before that claim ships in 2.0.0.

## 2.0.0 Definition Of Done

The release is complete only when all of the following are true:

- Commits 1-55 are accepted in order, and every required pentest reports PASS.
- Conventional all-feature builds succeed; high assurance is an explicit
  build/runtime policy, and feature unification never adds secret behavior to
  ordinary types.
- The ordinary codec has strict, forgiving, incremental, one-shot, in-place,
  formatting, append, chunked, synchronous, and asynchronous APIs with
  documented allocation, rollback, committed-prefix, and post-error contracts.
- Runtime-created alphabets and codec values are validated, immutable,
  allocation-free under `no_std`, and usable across the applicable ordinary
  surfaces. Strict defaults remain canonical; padding-indifferent and
  noncanonical-trailing-bit behavior is explicitly named and cannot enter
  secret APIs.
- Strict RFC 4648 Standard and URL-safe padded/unpadded presets are first-class
  named APIs, and the ordinary defaults are documented aliases of the
  corresponding strict behavior.
- The exact RFC 4648 text, source manifest, checksum, errata decisions, and
  complete requirement mapping are retained and verified offline in the
  repository but excluded from every published package.
- Named PBKDF2-adapted, BinHex, bcrypt, crypt, and IMAP alphabet values are
  available without implying complete surrounding protocols. Exact IMAP,
  Passlib PBKDF2, and SHA-crypt transforms remain in their scoped companions.
- Secret operations are explicit, scalar, constant-time-oriented, staged or
  protected as required, redacted, and wiped on every supported unwind/return
  path, with abort, process termination, deliberate destructor suppression,
  caller-owned input, and historical/system-copy exclusions stated explicitly.
- Secret timing claims end at the final result gate. Symbol processing and
  validity accumulation are fixed-work within their documented public-length
  classes; success-only plaintext release and declassification are public and
  may add a length-proportional copy afterward.
- Secret in-place decode validates before mutation; secret streaming releases
  plaintext only from bounded frames or after explicit declassification. Its
  progress and work schedule depend only on public lengths, capacities, and
  padding mode, not byte validity, padding position, or trailing-bit values.
- No safe crate implementation originates a panic for malformed input,
  representable capacity/resource exhaustion, arithmetic overflow, or legal
  state-machine calls. Documented crate panics are limited to programmer or
  const-contract misuse; caller trait/provider panics may propagate while
  crate-owned secret state is cleaned on supported unwinding paths.
- Custom alphabets and wrapping policies are validated values; invalid codec
  specifications cannot be constructed through safe public APIs.
- Every SIMD implementation is listed in the release-facing verification
  table. Every backend advertised as admitted has real-hardware correctness,
  cleanup, fallback, and performance evidence. Included RVV or SVE candidates
  without that evidence remain explicitly non-dispatchable and are never
  described as production acceleration.
- Admitted native SIMD has a documented `no_std` static path where the compiler
  proves the ISA or an unsafe caller supplies the full deployment contract.
  Safe unsupported `no_std` configurations remain scalar.
- RFC 2045 MIME transfer bodies, RFC 7468 PEM, Base64-family multibase, the RFC
  3501 modified-UTF-7 payload transform, exact admitted password-record
  transforms, and pinned-version OpenPGP armor are complete within their
  named boundaries and have retained interoperability corpora.
- All companion crates use the shared 2.0 core contracts and are versioned as
  the `2.0.0` family.
- Core and companion adapters pass the same versioned semantic conformance
  corpus. Successful semantics agree; failures obey documented per-surface
  mutation and redaction contracts without unintended drift.
- High-assurance protected-memory claims are allocation-specific and
  lifetime-bound. Every distinct plaintext allocation is attested; a direct
  typestate path preserves one stable allocation through validation, while a
  two-allocation path attests staging and destination independently.
  Capabilities cannot survive reallocation, unlock, or degradation.
- Protected teardown has one owner at every reachable point and one ordered
  attempt per consumed handle when close or destruction executes. Cleanup
  failures are redacted, generation-degrading, and conservatively quarantined;
  the release does not claim cleanup when destruction is suppressed or a
  platform teardown step fails.
- Lifecycle ownership and its pending teardown stage are independent from wipe
  evidence, physical OS protection, and resource accounting. Later-stage
  failure preserves valid earlier evidence, while `Closed` requires all four
  axes to reach their successful terminal conditions.
- Every retryable teardown sub-operation is idempotent, conclusive-atomic, or
  generation-journaled. Successfully applied work is never repeated, partial
  accounting retains exact progress, and indeterminate disposal terminates in
  a non-addressable accounting tombstone rather than risking double-free.
- The default teardown journal is explicitly volatile and scoped to one live
  process/provider-instance generation. Termination invalidates recovery
  identities, restart is not recovery, and any persistent provider has separate
  accepted atomicity, durability, corruption, replay, and metadata evidence.
- Active, reserved, quarantined, and tombstoned identities share finite provider
  budgets. Quarantine/journal capacity is reserved before plaintext
  materialization; repeated failures have bounded memory, page, registry,
  tombstone, and retry cost; and permanent quarantine or an indeterminate
  disposal tombstone shuts the provider down without storage reuse.
- Verified full-range wiping gates every confidentiality-reducing teardown
  action at the posture required by the active policy. Wipe verification is an
  operational logical-range result, not proof of erasing historical/system
  copies. Failure preserves conservative accounting, invokes no later hook, and
  can end only in bounded full-wipe recovery or permanent non-reusable
  quarantine until process teardown.
- Physical protection posture is independent from conservative accounting.
  Unknown OS status remains fully charged but is reported as unknown, blocks
  high-assurance admission and new capabilities, and cannot regain an attested
  claim without successful re-establishment/re-query and fresh attestation.
- The supported scalar/SIMD WASM loader and artifacts are published as the
  versioned `2.0.0` JavaScript/npm companion.
- Kani, fuzzing, timing/codegen, Miri, sanitizers, cross-platform, MSRV,
  package, SBOM, and clean-room evidence is archived for the exact tag commit.
- Rust `1.90.0` remains the enforced workspace MSRV for the complete 2.0
  package family; support is not lowered to imitate comparison crates.
- Documentation makes no claim broader than the implementation and evidence.
- The signed `v2.0.0` tag is created only after the exact final commit is green
  in required GitHub checks.
