# 2.0 Incremental Encoder

Release target: `2.0.0`

Commit 9 implemented the heapless ordinary encoder that later one-shot, I/O,
async, and companion APIs share. Commit 12 exposes it through every public
`Base64<Spec>` codec while retaining the frozen 1.3.9 API as a compatibility
subset.

## State Bound

`EncoderState` owns one complete validated codec setting, at most two
incomplete input bytes, at most four pending encoded bytes, exact source
position state, and no allocation. It has no `Drop` implementation, wiping,
secret marker, I/O trait, or feature-dependent field. Commit 20 defines a
separate secret encoder state.

Retaining one pending encoded quantum is required for one-byte output chunks.
Once three accepted input bytes form a quantum, the input is never requested
again. Its four canonical symbols are retained and drained exactly once over
later calls.

## Update Contract

`update(input, output)` preflights the complete source span before mutation.
It then calculates the exact input prefix that can be accepted with the
current fixed-size state and output capacity. That source progress is committed
before input or destination mutation.

- `Progress::input_consumed` is the exact accepted input prefix.
- `Progress::output_produced` is the exact initialized output prefix.
- `NeedInput` means all supplied input was accepted and no encoded output is
  pending.
- `OutputFull` means encoded output remains pending. Its minimum retry output
  is one byte, and retrying does not re-consume input.
- Position overflow and internal lifecycle faults are absorbing and occur
  before this call mutates input-derived state or output.

The encoder accepts every byte value. There is no malformed-input or forgiving
encode mode.

## Finish And Reset

`finish(output)` emits the canonical two-, three-, or four-symbol tail selected
by the codec's padding policy. A short destination returns retryable
`OutputFull` and retains the exact undelivered suffix. Successful completion is
idempotent: later `finish` calls return `Complete` with zero progress. New
input after completion is rejected until `reset`.

`reset` starts one unrelated ordinary message at source position zero and
clears logical pending state. This is ordinary cleanup, not a secret erasure
claim.

## Canonical Output

Every strict encoder emits only the selected validated alphabet and its exact
padding policy:

| Codec | Tail policy |
|---|---|
| Strict Standard padded | canonical `=` padding |
| Strict Standard unpadded | no padding |
| Strict URL-safe padded | canonical `=` padding |
| Strict URL-safe unpadded | no padding |

Runtime codecs use their owned validated alphabet and validated encode-padding
policy. Compatibility decode settings cannot create a noncanonical encoder.

## Evidence

- RFC 4648 Section 10 vectors run through all four strict encoders and every
  input/output partition.
- Deterministic bounded binary inputs are compared with an independent oracle
  over every input/output partition.
- One-byte and zero-byte destinations exercise pending output and repeated
  `OutputFull` without duplicate consumption.
- Padded and unpadded tails drain one byte at a time.
- Debug, release, no-default-features, and Rust 1.90.0 checks cover the same
  state machine.
- Kani proves bounded progress and fixed-state invariants for symbolic input,
  output capacity, and finalization cases.
