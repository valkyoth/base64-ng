# 2.0 Backend Health And Quarantine

Commit 24 places every ordinary accelerated encode and strict-decode backend
behind an allocation-free, process-local health latch. Secret operations never
enter this machinery; they remain on the separate scalar
constant-time-oriented boundary.

## State Machine

Each operation/backend pair has an independent `NeverRun`, `Testing`,
`Healthy`, or `Quarantined` state and a monotonic generation. The first caller
that changes `NeverRun` to `Testing` runs a fixed known-answer test through a
direct backend entry point. Direct KAT calls cannot recurse into normal
dispatch. Concurrent or recursive callers that observe `Testing` immediately
use scalar instead of waiting or treating an incomplete test as success.

Successful KAT completion changes the state to `Healthy`. A failed KAT,
initializer panic, impossible state, or checked-output mismatch changes it to
`Quarantined`. Quarantine is permanent for the process and affects only the
specific ordinary operation/backend pair. Malformed caller input never changes
backend health.

`initialize_backends()` runs every backend KAT available to the current build
and CPU. Applications can call it during single-threaded startup to avoid
first-use latency. KATs detect persistent implementation, compiler, and target
faults; they do not prove every possible input or transient hardware behavior.

## Fast And Checked Execution

The normal `simd` mode performs sizing, capacity, alphabet, canonicality, and
health checks before accelerated output. The architecture rewrites in Commits
25 through 30 freeze the final infallible direct-kernel boundary for this fast
contract.

The `checked-backend` feature is explicit and never selected implicitly. It
produces accelerated and scalar output in bounded stack buffers, compares the
initialized lengths and bytes, and copies only a matching chunk to caller
output. A mismatch discards the suspect chunk, quarantines the accelerated
backend, and retries the complete operation once through scalar. Verified
prefixes may already be committed, but suspect bytes are never copied. A
successful scalar retry replaces the complete result while telemetry retains
the backend fault.

This mode adds work and stack-copy volume but no heap allocation. It remains an
ordinary public-data integrity mode, not a constant-time or secret mode.

## `no_std` Static Selection

`no_std + simd` has no runtime CPU probing. Safe dispatch and
`StaticBackendToken::for_compiled_target()` select acceleration only when the
complete compile-time target-feature bundle is present and pointer-width
atomics can maintain health and quarantine. Otherwise execution is scalar.

`StaticBackendToken::assume_supported` is unsafe and requires deployment proof
for CPU features, OS vector state, ABI behavior, thread migration, and the
current thread. The token is non-forgeable in safe code and deliberately
neither `Send` nor `Sync`. It bypasses probing only: KAT, generation,
quarantine, bounds, canonicality, and reporting still apply. Commits 25 through
30 expose architecture kernels through this token contract as each rewritten
backend is admitted.

Targets without pointer-width atomics cannot maintain this process-local latch
and therefore remain scalar even if vector target features are visible.

## Fork And Runtime Clone

On native Unix `std` targets, the latch records the process identifier while
testing. A child that inherits `Testing` changes it back to `NeverRun`,
increments the generation, and falls back until reinitialization completes.
`NeverRun` remains untested, `Healthy` remains healthy, and `Quarantined`
remains quarantined across a fork. Windows, wasm, `no_std`, and runtimes with
clone semantics that do not change the process identifier must call
`initialize_backends()` before concurrent operation and must not clone an
in-progress initializer.

## Reporting

Every operation report includes the active backend, health posture, monotonic
generation, and optional stable backend-fault identifier. A quarantined
candidate reports scalar active execution plus `quarantined` health. Ordinary
backend generations are independent from secret algorithm, wipe, assurance,
protected-memory, and provider generations.
