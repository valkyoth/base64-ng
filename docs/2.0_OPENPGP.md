# OpenPGP ASCII Armor Boundary

`base64-ng-openpgp` owns complete ordinary ASCII armor framing from RFC 9580
Section 6. It validates the armor type boundary, ordered headers, mandatory
blank separator, RFC 4648 Standard Base64 body, optional CRC-24 footer, and an
exactly matching closing boundary before returning decoded packet bytes.

The crate deliberately does not parse OpenPGP packets. `PGP SIGNED MESSAGE`
is also excluded because RFC 9580 cleartext signatures are a separate protocol
with dash escaping, canonical text hashing, `Hash` headers, and a nested
`PGP SIGNATURE` block.

## Checksum Policies

RFC 9580 requires an implementation not to reject an object solely because a
CRC-24 footer is present, missing, malformed, or mismatched. Therefore:

- `ChecksumPolicy::Rfc9580` accepts all four states and exposes the observed
  `ChecksumStatus`.
- `ChecksumPolicy::RequireValidCrc24` is a separately named stricter
  application policy. It is not presented as RFC 9580's required behavior.
- `ChecksumGeneration::Omit` is the default and follows RFC 9580's recommendation.
- `ChecksumGeneration::LegacyCrc24` exists only for interoperability with
  implementations that still require the obsolete integrity footer.

The companion cannot infer packet-version contexts without parsing packets.
Callers must not request `LegacyCrc24` where RFC 9580 Section 6.1 forbids it.

## Resource And Release Rules

`OpenPgpLimits` independently bounds source bytes, generated bytes, decoded
bytes, physical-line length, header count, total header bytes, boundary label
length, block count, adjacent-document whitespace, and work before output.
Only ASCII whitespace is accepted outside armor blocks; other adjacent text is
rejected as ambiguous.

One-shot generation leaves caller-owned output unchanged on error. Incremental
objects retain bounded input or payload and release output only at `finish`.
Standard writer APIs validate the whole generated block before the first write,
but an underlying writer failure can still commit a visible prefix. Generation
checks the longest boundary, header, body, or checksum line actually emitted;
configurations with a physical-line limit below 76 remain usable when the
selected payload never produces a 76-character body line.

Synchronous reader and writer adapters validate every returned byte count.
Safe but contract-violating `Read` or `Write` implementations that over-report
their supplied buffer are rejected as `Io` errors instead of reaching a slice
panic. Such in-process implementations remain outside the crate's control and
must not be reused after violating their trait contract.

Ordinary APIs return normal memory. With `secrets`,
`parse_secret_armor_block` requires exactly one caller-expected armor type,
wipes the compacted encoded body, defers body-symbol, padding, and trailing-bit
validation to the core fixed-work secret frame, and returns clear-on-drop
storage. Equal-length malformed body-symbol positions therefore reach the same
fixed-work Base64 gate. Armor boundaries, headers, physical-line limits, block
selection, and checksum metadata are public protocol structure and remain
ordinary data-dependent parsing. Packet semantics remain the caller's
responsibility.

## Evidence

The repository locks the exact RFC 9580 July 2024 text, all seven current RFC
Editor errata records, and a requirement ledger. None of the current errata
changes Section 6 armor. Tests cover the official inline-signed message vector,
all four ordinary labels, CRC-24's standard check value, every checksum state,
every finite limit, malformed framing, all two-chunk partitions, one-byte
incremental input, short and over-reporting I/O, redaction, secret selection,
deferred secret body validation at every symbol position, and exact
generated-line limits. The retained fixture is differentially dearmored by
GnuPG and Sequoia `sq` when both tools are installed.

Run the focused gate with:

```sh
scripts/check-2.0-openpgp.sh
```
