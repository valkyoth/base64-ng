# base64-ng 2.1.0 Commit Release Plan

Status: planned; implementation has not started.
Plan date: 2026-09-30.
Baseline: signed `v2.0.4`, commit
`816da2e1e4a66c913057c86d149068f1c88776bf`.

2.1.0 improves ordinary decode throughput while preserving existing public
contracts and giving callers an explicit scalar-reference validation option.
This document is the executable roadmap for that work. The
[2.0 plan](2.0.0-release-plan.md) remains historical release context.

## Motivation And Verified Baseline

The comparison reviewed at `base64-turbo` commit
[`ec719d7573015500168392d93391bc933ce59c57`](https://github.com/hacer-bark/base64-turbo/tree/ec719d7573015500168392d93391bc933ce59c57)
uses `base64-ng 2.0.4` with `simd`, caller-owned buffers, and
`STANDARD.decode_slice`. Its measurements identify a real throughput problem;
they are not evidence that our SIMD feature was disabled.

Two implementation paths need attention:

- Historical `Engine::decode_slice` reaches SIMD through
  `src/decode_backend.rs`. Each x86 SIMD slice wrapper first validates the
  entire input with `scalar::validate_decode`, then classifies and decodes
  full blocks with vector instructions. NEON, wasm, and RVV also perform
  scalar prevalidation. The scalar pass limits the combined throughput.
- Canonical `Base64<S>::decode_into` in `src/v2/ordinary.rs` validates by
  driving the incremental decoder into a three-byte scratch buffer, then
  writes using its own scalar loop. Optimizing the historical API alone
  would leave the recommended 2.0 API behind. Allocating and append helpers
  can repeat validation through their forwarding calls.

Our retained Commit 34 Standard padded AVX2 median at a 64 KiB raw payload is
about 853 MiB/s of **decoded payload**. The competitor reports about 904 MiB/s
of **encoded input** on its AMD host. These different numerators, processors,
and compiler environments prevent an exact ratio comparison. They do support
the same general observation: present decode throughput is far below the
potential of the vector kernels. Commit 2 normalizes both byte measures.

The current admission gate establishes an advantage over our scalar fallback;
it does not establish competitiveness with other libraries. 2.1.0 retains
correctness admission and adds comparisons of complete public operations.

## Version And Scope Decisions

- Target release: `2.1.0`, with additive public APIs and compatible behavior.
- The existing synchronized major/minor policy applies: Rust package family
  versions become `2.1.0` during implementation. Changed wasm artifacts and
  the npm loader are also released as `2.1.0`. Later maintenance patches keep
  the selective-patch policy described in [RELEASE.md](RELEASE.md).
- This planning commit changes documentation only. Commit 1 prepares blocked
  development metadata; it does not authorize publication or tag creation.
- MSRV remains `1.90.0`. The current pinned release toolchain is `1.98.1`.
  Any subsequent toolchain/tool update is explicit and precedes final evidence.
  Kani records its actual verifier/compiler pairing separately.
- Scope includes ordinary strict Standard and URL-safe, padded and unpadded
  decoding on currently admitted SSSE3/SSE4.1, AVX2, AVX-512 exact/static,
  NEON, wasm simd128, and exact-profile Linux SpacemiT X60 RVV surfaces.
- Custom alphabets, relaxed policies, wrapping, whitespace processing, and
  protocol grammars retain their existing acceptance rules. Forwarding into
  the optimized strict core is allowed only where those rules match exactly.
- Existing SVE candidates, other RISC-V profiles, and big-endian fallbacks
  retain their admission status. This release does not require new hardware
  families or broaden their deployment claims.
- Secret/CT algorithms and their assurance/cleanup contracts remain separate.
  No ordinary validation policy is presented as a secret-decoding policy.
- Core runtime dependencies remain zero. Encoding behavior is preserved;
  existing encode performance is checked for regressions, not redesigned.

## Public Policy Model

Names below are design proposals, frozen in Commit 3 before implementation
depends on them. Validation strategy does not change the Base64 alphabet,
padding, trailing-bit, or compatibility grammar.

| Choice | Work | Destination contract | Intended use |
| --- | --- | --- | --- |
| Scalar execution | Scalar validation and scalar decode | Existing contract for the selected API | Deployments choosing scalar execution |
| Scalar-reference validation | Full scalar validation, then admitted SIMD decode when available | Existing contract for the selected API | Retain the current prevalidation approach explicitly |
| Automatic accelerated validation | Full SIMD validation where admitted, then decode; scalar fallback elsewhere | Existing contract for the selected API | Normal ordinary throughput after admission |
| Progressive decode, conditional | Combined validation/decode with explicit committed progress | May modify a documented prefix on failure | Opt-in maximum-throughput ordinary processing |
| Existing CT secret APIs | Existing separate scalar secret implementation | Existing secret staging and cleanup contract | Secret-bearing frames |

Provide validation strategy through an additive per-call option or an ordinary
decoder configuration wrapper. Prefer one small non-exhaustive policy enum,
provisionally `DecodeValidation::{Auto, ScalarReference}`. Avoid new fields in
publicly constructible structs, changes to the sealed `Codec` trait, or changes
to existing incremental `decoder()` semantics. Do not add a mutually exclusive
Cargo feature: feature unification must not change a caller's policy choice.

Existing ordinary calls use the admitted automatic strategy after Commit 18.
`ScalarReference` always performs complete scalar validation, even on SIMD
hardware; it does not promise scalar output generation or constant time.
Scalar-only builds and existing deployment checks continue to work. A runtime
policy assertion is not itself an instruction to change dispatch.

`checked-backend` remains an additive redundant output-comparison mode. No new
policy, wrapper, or static-token method may bypass its scalar comparison,
quarantine, and retry rules. Document that it costs more than scalar-reference
prevalidation and supplies different evidence.

The earlier illustrative `STANDARD.decoder().validation(...)` syntax is not
an API commitment. The final design must fit both the historical `Engine` and
canonical `Base64<S>` surfaces without breaking their existing methods.

## Non-Negotiable Contracts

1. Strict RFC 4648 acceptance remains exact, including zero unused tail bits,
   required/forbidden padding, alphabet separation, and trailing-data rejection.
2. Preserve each existing API's error type, original index, and error precedence.
   A cheap length/capacity check may compute information early but must not
   return before a higher-priority error defined by that surface. In particular,
   canonical one-shot validation precedes output/allocation-limit failure.
3. Canonical `*_into` and existing transactional APIs leave the entire
   destination unchanged on every returned error. Historical scalar
   `decode_slice` can commit a prefix on error; inventory its actual behavior
   rather than incorrectly promising universal rollback across old APIs.
4. Vector validation produces no caller-visible decoded bytes. It validates
   complete interior blocks and exact scalar tails before destination writes.
   SIMD rejection uses the appropriate scalar reference to recover diagnostics.
5. A private validated-input representation, if introduced, binds immutable
   input, exact length, complete codec settings, and any execution assumptions.
   It is not forgeable by callers or reused for different bytes or policies.
   Safe APIs never accept an unchecked "already validated" claim.
6. The write phase has proven bounds and no recoverable input error. If an
   injected backend fault can occur after writes, recovery must complete via
   validated scalar output, or staging must prevent an error with changed
   transactional output. Merely calling a phase "infallible" is insufficient.
7. Preserve CPU/OS detection, exact-width accesses, KATs, quarantine, generation
   checks, static-token rules, and existing register/scratch cleanup. Invalid
   caller input is not a backend health fault.
8. Ordinary accelerated modes remain input-dependent. Do not claim constant
   time, stronger memory protection, or weaker validation from their speed.
9. All allocating/append/protocol helpers retain their bounds, reservation
   ordering, rollback, and failure contracts. One-pass output is never selected
   implicitly by an API that promises transactionality.

## Commit And Pentest Workflow

Use subjects such as `Commit 1 (2.1.0): Establish decode release baseline`.
Corrections use `Commit 6a (2.1.0): ...`, preserving the numbered ownership
boundary. Do not rewrite reviewed or pushed history. This plan-only commit
does not consume Commit 1.

Every numbered checkpoint has a goal, deliverables, verification, and exit
criteria below. Run focused checks for that change and the existing standard
gate as appropriate before committing. Keep ordinary per-commit CI independent
of whether long-duration release campaigns have been collected yet.

For each pentest handoff give full immutable hashes:
`<last-accepted-hash>..<checkpoint-head-hash>` (exclusive base, inclusive head),
plus `git diff <base> <head>`. For a batch beginning with Commit N, use the
parent of Commit N as the base. Include all remediation commits. A maintainer
may request a contiguous batch; a checkpoint is release-accepted only when an
external PASS covers it. Temporary `PENTEST.md` is removed after disposition;
the final normalized report and release policy return to the normal permanent
report workflow.

Each checkpoint starts pending. When implemented, add its actual hash, check
results, and review range next to its entry. Record skipped/unavailable
execution honestly. A test that silently skips an unavailable ISA is not
evidence for admitting that ISA.

## Numbered Commits

### Commit 1: Establish decode release baseline

**Goal:** Make 2.1 development and its compatibility boundary unambiguous.

**Deliverables:** Prepare synchronized `2.1.0` development-blocked metadata,
generalizing existing version checks that hard-code the 1.3.9-to-2.0 transition.
Inventory public decode routes, errors, output behavior, supported hardware,
and reference/checked/secret paths. Preserve 2.0.4 API snapshots and release
records. Record the exact benchmark and compiler baselines.

**Verification:** Metadata/version/publish-plan fixtures must reject publishing
a development candidate. Compile representative 2.0.4 consumers unchanged;
run MSRV and public API checks. Confirm no codec behavior changed.

**Exit Criteria:** Development is correctly labeled and publishing blocked;
pentest the metadata controls and compatibility inventory before acceptance.

### Commit 2: Retain independent correctness and throughput baselines

**Goal:** Measure complete public APIs and make semantic regressions visible.

**Deliverables:** Extend isolated `perf/` to compare historical slice,
canonical slice, validation-only, and allocating decode separately. Retain
scalar/exact-backend rows and exact-pinned comparator revisions. Use the
independent RFC oracle and 2.0.4 differential fixtures for diagnostics and
multi-fault error precedence. Include allocation and dispatch observations.

**Verification:** Correctness-check output outside timing; use runtime input,
black-boxed results, random and structured payloads, block boundaries, 32 B,
512 B, 4 KiB, 64 KiB, and larger cache/memory cases. Report encoded-input and
decoded-payload throughput separately. Test that the harness detects wrong
output and error-only benchmark calls.

**Exit Criteria:** Reproducible baseline and limitations are recorded;
pentest the oracle independence, measurement boundaries, and provenance.

### Commit 3: Add explicit ordinary validation policy

**Goal:** Give callers a stable way to retain scalar-reference validation.

**Deliverables:** Freeze the additive policy API and implement it initially
using existing scalar/reference behavior. Cover `Engine` and `Base64<S>`,
validation/length operations, and an explicit configuration path for relevant
allocating helpers. Document precedence with `checked-backend`, static tokens,
and scalar-only deployments. Reserve progressive behavior for a distinct API.

**Verification:** Downstream compile tests, const/generic usage where already
supported, no-default/alloc/std/SIMD/checked feature combinations, MSRV, and
tests observing that a requested reference pass actually executes. Secret
types cannot acquire the ordinary option through implicit conversion.

**Exit Criteria:** Existing callers compile unchanged, policy cannot weaken
grammar or checked execution; pentest the API and feature composition.

### Commit 4: Build shared transactional validation infrastructure

**Goal:** Separate validation from writing with a reviewed internal contract.

**Deliverables:** Add checked sizing, interior-block/tail separation, private
validation results, and surface-specific diagnostic recovery. Preserve
required/forbidden padding and canonical tails. Keep reference validation
available; unsupported codec settings use the existing path. Freeze behavior
when the vector classifier and reference disagree.

**Verification:** Exhaust short inputs and tail bits, combined malformed and
small-output cases, high-bit bytes, padding in every position, overflow
boundaries, and whole-destination sentinels. Model validated-span bounds and
test that results cannot be reused for a different input or configuration.

**Exit Criteria:** The preflight/write boundary preserves every applicable
contract; pentest bounds, error precedence, and backend-fault recovery.

### Commit 5: Implement SSSE3/SSE4.1 validation

**Goal:** Establish the first vector validation pass for strict ordinary data.

**Deliverables:** Validate complete Standard/URL-safe blocks without output
stores, then use reviewed decode kernels and scalar tails. Add focused
internal routing for evaluation while the public automatic default retains
reference validation until final admission.

**Verification:** Every byte value at every lane; multiple invalid lanes;
unaligned and exact-length buffers; padding/tails across block boundaries;
reference error parity; protected-page boundary tests where available; native
execution and assembly checks for vector classification.

**Exit Criteria:** Correctness and transactionality pass on an executing host;
pentest new unsafe code and the validation-to-write boundary.

### Commit 6: Implement AVX2 validation and decode integration

**Goal:** Remove scalar prevalidation from the candidate AVX2 fast path.

**Deliverables:** Add a 32-byte validation pass with cross-lane validity
reduction and exact tail handoff. Share semantic preflight with Commit 4.
Measure loop unrolling only after the basic path is correct; preserve cleanup.

**Verification:** Lane-exhaustive and malformed-position tests, mixed
alphabets, multiple vector blocks, precise errors, output sentinels, guard
pages, assembly inspection, and same-process reference/candidate benchmarks.

**Exit Criteria:** No semantic or memory-safety regression and measured public
path improvement; pentest AVX2 lane reduction, loads, tails, and fallback.

### Commit 7: Implement AVX-512 VBMI validation

**Goal:** Improve the existing exact/static AVX-512 decoder safely.

**Deliverables:** Add 64-byte validation with correct high-bit rejection and
lane masks; retain exact 48-byte output stores and canonical scalar tails.
Preserve the complete feature/OS-state requirements. Automatic admission
remains a separate Commit 18 decision.

**Verification:** Every byte in all 64 lanes, masks near every boundary,
multiple failures, short/exact buffers, guard pages, actual AVX-512 execution,
generated-code inspection, and AVX2 comparisons on the same host.

**Exit Criteria:** Exact/static candidate is correct without assuming that
wider vectors are faster; pentest masked accesses, feature checks, and cleanup.

### Commit 8: Route canonical 2.0 strict APIs through the candidate core

**Goal:** Make the throughput work available to the recommended consumer API.

**Deliverables:** Connect the four strict presets and exactly equivalent
runtime settings to shared validated decoding. Keep canonical `OneShotError`
and historical `DecodeError` diagnostics distinct. Accelerate eligible
`validate`/`decoded_len` operations as well as writing; retain custom/relaxed
scalar paths and explicit reference selection.

**Verification:** Independent-oracle and 2.0.4 behavioral parity, transactional
sentinels for every failure class, no-alloc checks, API-specific precedence,
runtime-policy tests, and benchmarks proving canonical calls reach the tested
implementation rather than an unrelated scalar loop.

**Exit Criteria:** Historical and canonical APIs both benefit without changing
their individual contracts; pentest routing and diagnostic translation.

### Commit 9: Implement NEON validation

**Goal:** Bring the same ordinary optimization to admitted little-endian ARM.

**Deliverables:** Add NEON validation with all-lane reduction and shared strict
tail handling. Preserve static no_std support, exact-width loads/stores,
register cleanup, health checks, and endian restrictions.

**Verification:** Exhaustive lane/byte and malformed-boundary tests, native
Apple Silicon and AWS AArch64 runs, checked/static feature tests, assembly

**Exit Criteria:** Native correctness is retained separately for each host;
pentest NEON code and hardware evidence before changing default routing.

### Commit 10: Implement wasm simd128 validation and loader integration

**Deliverables:** Add vector validation to the SIMD artifact; keep scalar

**Verification:** Deterministic artifacts, exact npm tarball/install tests,

### Commit 11: Implement RVV validation for the admitted X60 profile

**Goal:** Improve the existing native RVV path without broadening admission.

**Exit Criteria:** Required native access and evidence exist before admitting

### Commit 12: Integrate owners, append, and forwarding surfaces

**Goal:** Avoid repeated validation while preserving wrapper guarantees.

**Deliverables:** Reuse private validated results within allocating, bounded,

**Verification:** Inject reservation failures, count allocations, verify

Benchmarks count full wrapper work and repeated-pass elimination.

### Commit 13: Complete health, checked, static, and reporting composition

**Goal:** Ensure options cannot bypass integrity or deployment controls.

**Deliverables:** Cover new validators in backend KATs; integrate both

**Verification:** Inject false rejection, false acceptance, output mismatch,

**Exit Criteria:** Reports describe actual execution and no option bypasses

### Commit 14: Decide the progressive API from measured benefit

**Goal:** Justify an additional public contract before expanding the API.

**Deliverables:** Build a private one-pass prototype and compare it with the

above 4 KiB, supported by paired repeated samples on a named native host.

**Verification:** Validate outputs, injected late errors, committed-prefix
accounting, equal build settings, resource bounds, and prototype semantics.
Record either the measured case for shipping or an explicit decision to omit.

**Exit Criteria:** Pentest the proposed contract and evidence. A no-go decision
completes this conditional scope; it creates no promised future feature.

### Commit 15: Complete the progressive decision

**Goal:** Ship a strictly validating opt-in operation only if justified.

**Deliverables:** On go, expose the separately named progressive operation

**Verification:** On go, fuzz chunk/capacity schedules, late malformed data,

**Exit Criteria:** No ambiguous "unchecked" ordinary API or partial-output

## Release Completion Definition

2.1.0 is complete when users can retain scalar-reference prevalidation or use
measurably faster admitted ordinary decoding through the documented public
APIs, with existing grammar, diagnostic, output, resource, and secret contracts
preserved. The progressive API is either tested and admitted or explicitly
omitted by the recorded decision. Every checkpoint is reviewed and all release
requirements pass. Correctness/security findings block release; a calendar or
benchmark target never overrides them.
