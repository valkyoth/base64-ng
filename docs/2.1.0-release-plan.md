2.1.0 improves ordinary encode/decode throughput across one-shot, streaming,
and in-place APIs while preserving existing public contracts and giving callers
an explicit scalar-reference validation option. It also adds a borrowed
validated-input view and discoverable companion acceleration features.

[2.0 plan](2.0.0-release-plan.md) remains historical release context.

## Motivation And Verified Baseline

The comparison reviewed at `base64-turbo` commit
[`ec719d7573015500168392d93391bc933ce59c57`](https://github.com/hacer-bark/base64-turbo/tree/ec719d7573015500168392d93391bc933ce59c57)
uses `base64-ng 2.0.4` with `simd`, caller-owned buffers, and
`STANDARD.decode_slice`. Its measurements identify a real throughput problem;
they are not evidence that our SIMD feature was disabled.

Two implementation paths need attention:

- Historical `Engine::decode_slice` reaches SIMD through
  `src/decode_backend.rs`. Each x86 SIMD slice wrapper first validates the
  entire input with `scalar::validate_decode`, then classifies and decodes
  full blocks with vector instructions. NEON, wasm, and RVV also perform
  scalar prevalidation. The scalar pass limits the combined throughput.
- Canonical `Base64<S>::decode_into` in `src/v2/ordinary.rs` validates by
  driving the incremental decoder into a three-byte scratch buffer, then
  writes using its own scalar loop. Optimizing the historical API alone
  would leave the recommended 2.0 API behind. Allocating and append helpers
  can repeat validation through their forwarding calls.

Our retained Commit 34 Standard padded AVX2 median at a 64 KiB raw payload is
about 853 MiB/s of **decoded payload**. The competitor reports about 904 MiB/s
of **encoded input** on its AMD host. These different numerators, processors,
and compiler environments prevent an exact ratio comparison. They do support
the same general observation: present decode throughput is far below the
potential of the vector kernels. Commit 2 normalizes both byte measures.

The current admission gate establishes an advantage over our scalar fallback;
it does not establish competitiveness with other libraries. 2.1.0 retains
correctness admission and adds comparisons of complete public operations.

The user-facing performance scope also includes canonical encoding, which
currently uses a separate scalar loop; portable decoding, whose canonical
alphabet lookup scans up to 64 entries; incremental transforms used by I/O
adapters; and the scalar in-place decode write phase. Existing owned
`Base64String` support does not provide a borrowed validated-input view.
These are explicit implementation checkpoints below, not just routing audits.

## Version And Scope Decisions

- Target release: `2.1.0`, with additive public APIs and compatible behavior.
- The existing synchronized major/minor policy applies: Rust package family
  versions become `2.1.0` during implementation. Changed wasm artifacts and
  the npm loader are also released as `2.1.0`. Later maintenance patches keep
  the selective-patch policy described in [RELEASE.md](RELEASE.md).
- This planning commit changes documentation only. Commit 1 prepares blocked
  development metadata; it does not authorize publication or tag creation.
- MSRV remains `1.90.0`. The current pinned release toolchain is `1.99.0`.
  Any subsequent toolchain/tool update is explicit and precedes final evidence.
  Kani records its actual verifier/compiler pairing separately.
- Scope includes ordinary strict Standard and URL-safe, padded and unpadded
  decoding on currently admitted SSSE3/SSE4.1, AVX2, AVX-512 exact/static,
  NEON, wasm simd128, and exact-profile Linux SpacemiT X60 RVV surfaces.
- Custom alphabets, relaxed policies, wrapping, whitespace processing, and
  protocol grammars retain their existing acceptance rules. Forwarding into
  the optimized strict core is allowed only where those rules match exactly.
- Existing SVE candidates, other RISC-V profiles, and big-endian fallbacks
  retain their admission status. This release does not require new hardware
  families or broaden their deployment claims.
- Secret/CT algorithms and their assurance/cleanup contracts remain separate.
  No ordinary validation policy is presented as a secret-decoding policy.
- Core runtime dependencies remain zero. Canonical ordinary encoding reuses
  existing admitted kernels rather than introducing a new encoder algorithm.
  Portable scalar, incremental, adapter, and in-place improvements preserve
  each surface's existing semantics and feature defaults.
- Ship a safe borrowed validated-input view, provisionally `Base64Ref<'a, S>`,
  after the private validation boundary is established. Only the progressive
  API remains conditional on measured benefit; the borrowed view is committed
  release scope.
- Add optional companion acceleration feature forwarding. Do not add unchecked
  decoding, automatic alphabet guessing, internal thread pools, or unrelated
  protocol crates as part of this release.

## Public Policy Model

Names below are design proposals, frozen in Commit 3 before implementation
depends on them. Validation strategy does not change the Base64 alphabet,
padding, trailing-bit, or compatibility grammar.

| Choice | Work | Destination contract | Intended use |
| --- | --- | --- | --- |
| Scalar execution | Scalar validation and scalar decode | Existing contract for the selected API | Deployments choosing scalar execution |
| Scalar-reference validation | Full scalar validation, then admitted SIMD decode when available | Existing contract for the selected API | Retain the current prevalidation approach explicitly |
| Automatic accelerated validation | Full SIMD validation where admitted, then decode; scalar fallback elsewhere | Existing contract for the selected API | Normal ordinary throughput after admission |
| Progressive decode, conditional | Combined validation/decode with explicit committed progress | May modify a documented prefix on failure | Opt-in maximum-throughput ordinary processing |
| Existing CT secret APIs | Existing separate scalar secret implementation | Existing secret staging and cleanup contract | Secret-bearing frames |

Provide validation strategy through an additive per-call option or an ordinary
decoder configuration wrapper. Prefer one small non-exhaustive policy enum,
provisionally `DecodeValidation::{Auto, ScalarReference}`. Avoid new fields in
publicly constructible structs, changes to the sealed `Codec` trait, or changes
to existing incremental `decoder()` semantics. Do not add a mutually exclusive
Cargo feature: feature unification must not change a caller's policy choice.

Existing ordinary calls use the admitted automatic strategy after Commit 25.
`ScalarReference` always performs complete scalar validation, even on SIMD
hardware; it does not promise scalar output generation or constant time.
Scalar-only builds and existing deployment checks continue to work. A runtime
policy assertion is not itself an instruction to change dispatch.

`checked-backend` remains an additive redundant output-comparison mode. No new
policy, wrapper, or static-token method may bypass its scalar comparison,
quarantine, and retry rules. Document that it costs more than scalar-reference
prevalidation and supplies different evidence.

The earlier illustrative `STANDARD.decoder().validation(...)` syntax is not
an API commitment. The final design must fit both the historical `Engine` and
canonical `Base64<S>` surfaces without breaking their existing methods.

The borrowed view retains immutable encoded bytes, the exact codec, and the
validated decoded length without copying the payload. Its final API is frozen
at its implementation checkpoint. Reusing grammar validation does not retain
an unconditional backend-health authorization: execution checks current health
and deployment rules. Explicit `ScalarReference` selection still runs the full
reference pass on each decode, and `checked-backend` still compares output.
The view is ordinary data, with no CT or secret-storage claim.

## Non-Negotiable Contracts

1. Strict RFC 4648 acceptance remains exact, including zero unused tail bits,
   required/forbidden padding, alphabet separation, and trailing-data rejection.
2. Preserve each existing API's error type, original index, and error precedence.
   A cheap length/capacity check may compute information early but must not
   return before a higher-priority error defined by that surface. In particular,
   canonical one-shot validation precedes output/allocation-limit failure.
3. Canonical `*_into` and existing transactional APIs leave the entire
   destination unchanged on every returned error. Historical scalar
   `decode_slice` can commit a prefix on error; inventory its actual behavior
   rather than incorrectly promising universal rollback across old APIs.
4. Vector validation produces no caller-visible decoded bytes. It validates
   complete interior blocks and exact scalar tails before destination writes.
   SIMD rejection uses the appropriate scalar reference to recover diagnostics.
5. Private validation results and the public borrowed view bind immutable
   input, exact length, complete codec settings, and any execution assumptions.
   Their fields are private; callers cannot forge them or substitute bytes or
   policies. Safe APIs never accept an unchecked "already validated" claim.
6. The write phase has proven bounds and no recoverable input error. If an
   injected backend fault can occur after writes, recovery must complete via
   validated scalar output, or staging must prevent an error with changed
   transactional output. Merely calling a phase "infallible" is insufficient.
7. Preserve CPU/OS detection, exact-width accesses, KATs, quarantine, generation
   checks, static-token rules, and existing register/scratch cleanup. Invalid
   caller input is not a backend health fault.
8. Ordinary accelerated modes remain input-dependent. Do not claim constant
   time, stronger memory protection, or weaker validation from their speed.
9. All allocating/append/protocol helpers retain their bounds, reservation
   ordering, rollback, and failure contracts. One-pass output is never selected
   implicitly by an API that promises transactionality.
10. Incremental acceleration preserves per-call validation/mutation, progress,
    finalization, and partial-quantum contracts, including one-byte buffers.
    Streaming cannot promise whole-message rollback after earlier output was
    delivered. In-place SIMD requires an independently reviewed overlap-safe
    boundary; disjoint input/output kernels cannot simply alias their slices.

## Commit And Pentest Workflow

Use subjects such as `Commit 1 (2.1.0): Establish decode release baseline`.
Corrections use `Commit 6a (2.1.0): ...`, preserving the numbered ownership
boundary. Do not rewrite reviewed or pushed history. This plan-only commit
does not consume Commit 1.

Every numbered checkpoint has a goal, deliverables, verification, and exit
criteria below. Run focused checks for that change and the existing standard
gate as appropriate before committing. Keep ordinary per-commit CI independent
of whether long-duration release campaigns have been collected yet.

For each pentest handoff give full immutable hashes:
`<last-accepted-hash>..<checkpoint-head-hash>` (exclusive base, inclusive head),
plus `git diff <base> <head>`. For a batch beginning with Commit N, use the
parent of Commit N as the base. Include all remediation commits. A maintainer
may request a contiguous batch; a checkpoint is release-accepted only when an
external PASS covers it. Temporary `PENTEST.md` is removed after disposition;
the final normalized report and release policy return to the normal permanent
report workflow.

Each checkpoint starts pending. When implemented, add its actual hash, check
results, and review range next to its entry. Record skipped/unavailable
execution honestly. A test that silently skips an unavailable ISA is not
evidence for admitting that ISA.

## Release Completion Definition

2.1.0 is complete when users can retain scalar-reference prevalidation or use
measurably faster admitted ordinary decoding through the documented public
APIs, with existing grammar, diagnostic, output, resource, and secret contracts
preserved. Canonical encoding, portable scalar decoding, bulk streaming, and
in-place decoding have measured improvements on their named supported paths;
the borrowed validated view and companion feature switches are documented,
tested, and available. The progressive API is either tested and admitted or
explicitly omitted by the recorded decision. Every checkpoint is reviewed and all release
requirements pass. Correctness/security findings block release; a calendar or
benchmark target never overrides them.
