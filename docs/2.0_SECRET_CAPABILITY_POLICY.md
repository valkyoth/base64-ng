# 2.0 Secret Capability Policy

Status: implemented through Commit 22 for the `2.0.0` candidate.

## Capability Split

Ordinary public-data builds provide encoding, decoding, validation, bounded
buffers, and incremental state without accepting a secret cleanup policy.
They compile on supported native and `wasm32` targets without either cleanup
acknowledgement feature.

The dependency-free `secrets` feature enables structurally separate secret
owners and bounded scalar secret encode/decode states. It provides redacted
formatting, fixed-work-oriented alphabet processing, opaque malformed-input
errors, and best-effort cleanup. Cargo feature unification does not add fields,
destructors, or secret semantics to ordinary 2.0 values.

`allow-wasm32-best-effort-wipe` and
`allow-compiler-fence-only-wipe` are secret-only deployment
acknowledgements. They are no-ops for ordinary public-data builds. Neither is
an assurance upgrade.

## Cleanup Claim

Secret owners overwrite their complete owned or borrowed mutable ranges with
ordered volatile zero writes before release. Heap owners include initialized
bytes and spare capacity. Replacing a `SecretVec` wipes the displaced complete
allocation before it is released and wipes the incoming allocation's spare
capacity before adopting it.

This is best-effort data-retention reduction, not eradication. It cannot clear
historical copies, registers, compiler spill slots, cache lines, write buffers,
allocator metadata, prior allocations, swap, hibernation images, snapshots,
crash dumps, or storage outside the range owned by the secret type.

Borrowed `SecretInput` is immutable caller-owned memory. The crate classifies
but cannot wipe that input. The caller retains its cleanup responsibility.

RAII guards wipe secret staging on normal return, typed error, partial-state
drop used to model cancellation, and Rust panic unwinding. Destructors do not
run after OOM abort, `panic=abort`, process termination, deliberate
`mem::forget`, or equivalent destructor suppression. Panic guards therefore
protect unwinding only; they are not a process-failure recovery mechanism.

## High-Assurance Eligibility

`base64_ng_require_high_assurance` is a custom build cfg, not an additive
Cargo feature. Commit 22 makes it an eligibility gate that:

- requires the `secrets` capability;
- accepts x86/x86_64 native speculation barriers; and
- accepts AArch64 only with operator-supplied
  `base64_ng_aarch64_csdb_attested` evidence.

Other or unattested targets fail compilation regardless of whether ordinary
SIMD is enabled directly or through Cargo feature unification. A successful
eligible build does not attest protected storage by itself and is not enough to
authorize one secret operation. Commit 22 adds non-forgeable runtime assurance
tokens and allocation-specific `ProtectedSecret` capabilities. Assured
encode/decode requires both. On an eligible target, `secrets + simd` may compile
additively: ordinary calls may use an admitted backend, while assured secret
operations remain scalar and never accept an ordinary mutable slice as
protected storage.

The legacy `BackendPolicy::HighAssuranceScalarOnly` remains available when an
entire process must reject ordinary SIMD. It is stricter than the operation-
specific Commit 22 token and is not required merely to compile both capability
families into one binary.

## Evidence

`scripts/check-2.0-secret-capabilities.sh` verifies ordinary portability,
best-effort secret builds, structural separation, lifecycle cleanup, WASM
acknowledgement behavior, and the high-assurance compile matrix. The dedicated
secret storage, decoder, encoder, and in-place gates retain their deeper
semantic and cleanup tests. `scripts/check-2.0-assurance.sh` verifies the
Commit 22 token, typestate, provider, teardown, and attestation boundary.
