# 2.0 Release Freeze

Status: Commit 54 pre-seal RVV admission reopening

This document records the package, API, and claim boundary being prepared for
the final 2.0 external review. It does not authorize publication. The pre-seal
correction series, final pentests, exact evidence, Commit 55, required green
CI, and a signed `v2.0.0` tag remain mandatory.

## Package Family

All 13 Rust packages use version `2.0.0` and are selected by the
`synced-family` plan in `release-crates.toml`. The supported
`base64-ng-wasm-loader` npm package and its generated wasm artifacts also use
version `2.0.0`. `scripts/release_crates.py` defines dependency order and
refuses a dirty tree, a missing tag, or an invalid tag signature for a real
publication.

The frozen Rust APIs are stored under `api-snapshots/v2.0.0/`. The signed
1.3.9 compatibility inventory remains under `api-snapshots/v1.3.9/`.

## Reviewed Usability Reopening

Before the final full-range pentest, the release owner explicitly reopened the
pre-seal API boundary for two ordinary usability additions:

- policy-carrying, immutable `Base64String<S>` storage under `alloc`; and
- a focused ordinary `base64_ng::prelude` that excludes secret,
  compatibility, protocol, and historical APIs.

The additions require regenerated 2.0 API snapshots, migration and compile-fail
evidence, external review, and the same fail-closed release gate as every prior
surface. This section records the reviewed exception; it does not weaken the
rule that Commit 55 may contain only the normalized final pentest report.

## RVV Admission Reopening

The release owner reopened the pre-seal backend boundary after physical access
became available to a Banana Pi BPI-F3 with a SpacemiT X60 RVV 1.0 processor.
The native campaign is part of 2.0.0 rather than a 2.0.1 deferral. It must bind
correctness, Linux signal and thread context, ABI, generated assembly, register
cleanup, and paired scalar/RVV performance to one clean exact commit.

Any safe automatic dispatch added from this evidence is limited to the exact
reviewed Linux/X60 profile. Other RISC-V CPUs, non-Linux systems, unknown probe
results, and unavailable or denied vector state remain scalar. QEMU VLEN
128/256 evidence remains portability evidence only. The freeze resumes only
after the final implementation is recaptured on native hardware, externally
retested, and green in required CI.

## Behavioral Boundaries

- The 2.0 crate-root strict presets implement canonical RFC 4648 behavior.
- Forgiving web decode, legacy transport whitespace, line wrapping, and each
  protocol companion are explicitly named opt-in surfaces.
- Protocol companions implement only their documented transform boundary; they
  are not complete MIME, PEM, OpenPGP, IMAP, multibase, or password systems.
- Ordinary APIs may return detailed input errors. Secret APIs use bounded
  fixed-work processing, opaque errors, explicit exposure, and audited cleanup
  boundaries.
- SIMD is used only by admitted backends and operations. Unsupported targets,
  custom alphabets, and non-admitted surfaces retain scalar execution.

## Persistence Inventory

Base 2.0 ships no persistent teardown provider. `BestEffortProvider` is finite,
volatile, generation-scoped, and valid only within one live process instance.
Its journal orders bounded teardown attempts; it does not provide durable
write-ahead logging, restart recovery, crash recovery, or replay protection.
The unsafe extension protocol alone is not a stable persistent-provider API.

Persistent-provider inventory: **none**.

## Artifact Provenance

The wasm loader build emits `artifacts/PROVENANCE.json` beside its checksums.
The record binds the npm package name and version, both generated wasm artifact
digests, and the exact 40-character Git source commit. Packaging tests require
the same record in the npm archive.

Rust package contents are enumerated for every selected package. RFC source
text remains repository evidence and is excluded from published artifacts.
SBOM generation and reproducible package/build checks remain part of the stable
release gate.

## Final Gate

The pre-seal candidate must complete package, API, migration, documentation,
checkpoint, and release-process records before the final full-range pentest.
`scripts/stable_release_gate.sh candidate` then binds all required evidence to
that clean candidate. Commit 55 may add only the normalized final pentest report
at `security/pentest/v2.0.0.md`; it must not change evidence records, runtime
behavior, public API, or other documentation. Release mode either repeats the
campaign or accepts retained expensive evidence only after the metadata-only
equivalence gate proves unchanged protected repository contents. Original
campaign provenance is retained, while package, SBOM, and reproducibility
evidence is regenerated against the tag candidate before signing.
