# 2.0 Memory, Sanitizer, And Hardware Evidence

Status: Commit 53 evidence contract. Local tooling is implemented; the final
2.0.0 release campaign remains blocked until the native evidence marked
required below is retained against the exact candidate.

## Dynamic Analysis

| Evidence | Scope | Release interpretation |
| --- | --- | --- |
| Miri | Representative scalar, allocation, overlap, bytes, and Tokio cancellation paths | Detects interpreter-visible undefined behavior; not a whole-crate proof |
| AddressSanitizer | Ordinary and secret in-place overlap/cursor suites | Detects addressability and lifetime violations on the supported nightly target |
| LeakSanitizer | Heap secret ownership, success, error, and cleanup paths on x86-64 Linux | Detects reachable process-exit leaks in the selected campaign |
| ThreadSanitizer | Concurrent ordinary backend-health initialization on x86-64 Linux | Detects races in the selected shared-state campaign; protected providers remain separately classified |

UndefinedBehaviorSanitizer is not a separately supported Rust sanitizer. Safe
arithmetic and state-machine behavior is instead covered by checked arithmetic,
hostile-input tests, Miri, Kani, fuzzing, Clippy, and panic-policy gates. This
does not rebrand those tools as UBSan.

The AMD AVX-512 record supports only the named-host policy. A second,
preferably Intel, AVX-512 VBMI campaign is tracked as 2.0.1 corroboration and
must pass before any portable performance or frequency claim is introduced.

`scripts/check-2.0-memory-hardware-evidence.sh` never counts QEMU, cross-compile,
or generated assembly as native evidence. Setting
`BASE64_NG_REQUIRE_COMMIT53_NATIVE=1` makes missing retained Apple and Linux
NEON bundles fatal. Native reports must carry the exact source commit, CPU, OS,
firmware or microcode where available, compiler, commands, and checksums.

## Resource Evidence

The performance schema records core package binary bytes, core symbol counts,
allocation counts, fixed in-place stack staging, synchronous adapter object
sizes, and pending-output capacities for default, no-default, SIMD, secrets,
and checked-backend feature sets. Tokio and protocol companion limits are
tested independently by their package gates; companions are separate packages
and do not enter a core consumer unless selected as dependencies.

Parser and adapter ceilings are public constructor limits or fixed constants,
not observations inferred after allocation. Cross-crate semantic vectors run
through 2.0 one-shot and incremental core APIs, synchronous streams, bytes,
Tokio, serde, and sanitization. Successful bytes must agree. Rejections retain
the destination mutation, offset, EOF, and opaque-secret contract declared by
the corpus rather than forcing unlike APIs into one error shape.

## Secret Allocation And Cleanup

Heap secret encoder and decoder frames reserve complete output and staging
storage before classified input is accepted. Test-only allocation snapshots
assert pointer and capacity identity after every update. No growth after
plaintext materialization is permitted. The default protected provider also
reserves identity, logical-byte, effective-page, registry, quarantine, and
maintenance budgets before storage materialization.

Normal unwind runs the same cleanup owner as ordinary drop. Volatile provider
drop wipes provider-owned quarantined storage, but reconstructing a provider
creates a distinct identity and empty journal. Restart is not recovery and
makes no claim about storage owned by the terminated process.

Base 2.0 ships no persistent provider. Persistent process-kill, torn-write,
rollback, replay, authentication, filesystem, and power-loss campaigns are
therefore not applicable and cannot be inferred from the unsafe extension
protocol.

Abort, `panic=abort`, OOM abort, process termination, deliberate leaks or
destructor suppression, caller-owned input, historical compiler/register/cache
copies, swap, hibernation, and crash dumps remain outside the cleanup guarantee.
Deployments must control those boundaries separately.

## Release Gate

The candidate must retain:

- clean Miri and sanitizer manifests from the exact source;
- the versioned cross-crate semantic-corpus result;
- binary, symbol, stack, allocation, pending-buffer, and parser-limit evidence;
- native correctness and performance for every automatically dispatched
  hardware backend;
- QEMU/emulator reports labeled only as portability or candidate evidence;
- protected teardown fault traces, bounded resource tests, and volatile
  restart non-recovery tests; and
- external unsafe, sanitizer, cross-platform, hardware, and claim pentests.
