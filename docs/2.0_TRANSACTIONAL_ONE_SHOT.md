# 2.0 Transactional One-Shot Operations

Release target: `2.0.0`

Commit 12 exposes the first canonical 2.0 consumer surface while retaining the
complete 1.3.9 API as a compatibility bed. `Base64<Spec>` owns one validated,
sealed codec specification and provides heapless incremental state plus
transactional ordinary one-shot operations.

## Canonical Presets

The explicit strict RFC 4648 values are:

- `STRICT_STANDARD_PADDED`;
- `STRICT_STANDARD_UNPADDED`;
- `STRICT_URL_SAFE_PADDED`; and
- `STRICT_URL_SAFE_UNPADDED`.

The existing top-level `encode` and `decode` conveniences continue to mean
strict Standard padded RFC 4648 behavior. Their 2.0 implementation migration
does not create a second policy.

## Slice Atomicity

`encode_into` and `decode_into` return the exact initialized prefix length.
Bytes after that prefix are unchanged. Every returned error leaves the entire
destination unchanged.

Encoding computes its checked exact length before writing. Decoding first runs
the incremental validator to completion and obtains the exact decoded length.
Only after validation and destination sizing succeed does an infallible write
pass transform the same immutable input. No heap allocation is needed for
caller-slice operations.

Ordinary detailed input errors may contain rejected bytes and exact source
indexes. They must not be logged for secret-bearing input. These operations
are input-dependent ordinary APIs, not constant-time-oriented secret APIs.

## Allocating Operations

With `alloc`, `encode_to_string` and `decode_to_vec` use
`try_reserve_exact` before materializing output. Their `_with_limit` variants
accept a maximum output length and reject larger exact results before
reservation. Decode validates before either checking the allocation limit or
calling the allocator, so malformed input cannot trigger output allocation.

Reservation failures map to `OneShotError::AllocationFailed`; explicit limits
map to `OneShotError::AllocationLimitExceeded`. A process-aborting allocator is
outside Rust's returned-error contract and cannot be converted into either
variant.

No allocating secret operation is introduced by this commit. Commits 18-21
own secret storage and require final protected capacity before plaintext is
materialized, so a secret allocation cannot grow after decode begins.

## Runtime Specifications

`Codec` is public and sealed. Consumers may write generic integrations over
`Codec` or use `dyn Codec`, but cannot implement the trait or return mutable
settings. `CodecBuilder` constructs owned runtime codecs from a
`ValidatedAlphabet` and explicit padding/trailing-bit policies without heap
allocation. Relaxed policies remain ordinary-only and explicitly selected.

## Example

```rust
use base64_ng::STRICT_STANDARD_PADDED;

let mut encoded = [0u8; 8];
let written = STRICT_STANDARD_PADDED
    .encode_into(b"hello", &mut encoded)
    .unwrap();
assert_eq!(&encoded[..written], b"aGVsbG8=");

let mut decoded = [0u8; 5];
let written = STRICT_STANDARD_PADDED
    .decode_into(&encoded, &mut decoded)
    .unwrap();
assert_eq!(&decoded[..written], b"hello");
```
