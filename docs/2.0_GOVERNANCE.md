# 2.0 Governance Decision

Status: Accepted for implementation checkpoints

Decision date: 2026-07-31

Planning baseline: signed `v1.3.9` at
`5af9802e0fd8fe25a9b50481715e6dbc4a9b87ad`

Authoritative roadmap: [`../2.0.0-release-plan.md`](../2.0.0-release-plan.md)

## Decision

`base64-ng` 2.0 is developed as 55 ordered, signed Git checkpoints. Every
checkpoint is locally verified, externally pentested, and accepted before the
next checkpoint starts. The project publishes no intermediate 2.0 package and
creates no intermediate 2.0 tag. The only release produced by this program is
the final signed `v2.0.0` tag after Commit 55.

Everything listed in the authoritative plan is required for 2.0.0. Work may
not be moved to a post-2.0 release merely to preserve a date. If a
specification, implementation, supported-toolchain capability, real-hardware
result, or required security result is unavailable, 2.0.0 waits.

This decision changes governance and evidence requirements only. It does not
change the behavior or package metadata of the current 1.3.9 release.

## Numbered Commit Contract

Each implementation checkpoint uses the exact subject from the authoritative
plan:

```text
Commit 1: Freeze the 2.0 scope and evidence contract
Commit 2: Inventory the 1.x API and freeze the migration ledger
```

A finding remediation keeps the checkpoint number and adds a letter:

```text
Commit 2a: Address API inventory pentest findings
```

Numbered commits are never rewritten after they are pushed or externally
reviewed. One commit cannot claim two numbered checkpoints. The maintainer
reports the exact range from the previous accepted checkpoint through `HEAD`
for every pentest.

The checkpoint table in the authoritative plan is updated by the following
numbered checkpoint after the preceding checkpoint receives a PASS. This
avoids modifying the commit while it is under review. Commit 55 records the
final accepted checkpoint state and final release evidence.

## Acceptance And Evidence

A checkpoint is accepted only when all of the following are true:

1. Its stated deliverables are complete.
2. Its checkpoint-specific verification passes.
3. `scripts/checks.sh` passes.
4. The signed commit exists with the exact numbered subject.
5. The external pentest covers the stated commit range and reports PASS.
6. Any finding is fixed in a suffix commit and the complete range is retested.

Generated local evidence is written under `target/release-evidence/` and is
not treated as accepted merely because a command exited successfully.
Checkpoint acceptance records the exact commit, commands, toolchain versions,
target or hardware identity where applicable, skips, and external pentest
disposition in the plan's checkpoint record.

Root `PENTEST.md` remains temporary scratch input and is deleted after
triage. Final release evidence is retained in the repository under
`security/pentest/`, `release-notes/`, and the release-evidence documentation.
Commit 55 archives the exact-tag evidence required by the plan, including
checksums or immutable workflow/artifact references for evidence too large to
commit.

Missing, skipped, stale, or target-inapplicable evidence is labeled as such.
It cannot be represented as PASS. QEMU, compiler/codegen, runtime smoke, and
real-hardware evidence remain distinct evidence classes.

## External Capability Disposition

The retained comparisons with `base64` `0.23.0` and `base64ct` `1.8.3` guide
capability coverage; they do not create dependencies or trust inheritance.

The following capabilities belong in the zero-runtime-dependency core:

- strict Standard and URL-safe padded and unpadded RFC 4648 codecs;
- validated compile-time and runtime alphabets;
- validated immutable runtime codec configurations;
- one-shot, incremental, in-place, const, formatting, append, and chunked
  operations where the capability contract permits them;
- explicitly named ordinary compatibility policies;
- bounded scalar constant-time-oriented secret encoding and decoding;
- ordinary SIMD selected only through an admitted runtime or static ISA
  contract.

The following capabilities belong in separately reviewed protocol companions:

- MIME content-transfer bodies;
- RFC 7468 PEM;
- Base64-family multibase;
- IMAP modified-UTF-7 payload transforms;
- Passlib PBKDF2 and SHA-crypt field or record transforms;
- OpenPGP ASCII armor;
- the supported JavaScript/npm WASM loader.

The following are explicitly unsupported security claims unless the plan names
and proves a narrower capability:

- formal cryptographic constant-time behavior for arbitrary toolchains,
  targets, or surrounding protocols;
- total erasure of registers, caches, swap, snapshots, historical copies, or
  storage outside the owned logical allocation;
- cleanup when destruction is deliberately suppressed or the process
  terminates;
- persistent teardown recovery without a separately named and admitted
  persistent provider;
- safe runtime ISA selection in `no_std` without compiler proof or an explicit
  unsafe caller contract;
- panic containment for hostile caller-provided trait implementations or
  unsafe providers.

## Strict RFC 4648 Terminology

The 1.x `STANDARD`, `STANDARD_NO_PAD`, `URL_SAFE`, and `URL_SAFE_NO_PAD`
engines already implement strict RFC 4648 behavior. The 2.0 work does not
retroactively claim that 1.x lacked RFC conformance.

For 2.0, "strict RFC 4648" means canonical encoding and decoding under the
selected Standard or URL-safe alphabet and padding policy. Strict decoding:

- accepts only the configured alphabet;
- rejects non-alphabet whitespace and mixed alphabets;
- rejects impossible lengths;
- rejects malformed, missing, excess, or forbidden padding;
- rejects trailing data after terminal padding;
- rejects non-zero unused trailing bits; and
- emits or accepts only the canonical representation selected by the codec.

Forgiving, legacy-whitespace, wrapped, and protocol-specific behavior is
separately named. Merely using the Standard alphabet does not make a codec
strict.

## RFC Source Policy

Commit 4 implements the source lock. Its requirements are frozen now:

- obtain the exact unmodified RFC 4648 bytes from an allowlisted RFC Editor
  HTTPS URL;
- retain the source URL and retrieval metadata separately from the RFC bytes;
- lock the file with SHA-256;
- reject byte and line-ending drift during offline verification;
- retain reviewed RFC Editor errata and project decisions separately from the
  immutable RFC text;
- map normative RFC 4648 requirements to implementation and independent tests;
- require an explicit reviewed update when source, errata, or interpretation
  changes; and
- exclude the RFC text and source-lock material from every crates.io and npm
  package unless a later checkpoint explicitly proves a need to publish it.

The local RFC copy is reference evidence, not executable code and not a
substitute for independent tests.
