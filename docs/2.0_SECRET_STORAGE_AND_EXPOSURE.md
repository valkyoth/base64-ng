# 2.0 Secret Storage And Explicit Exposure

Commit 18 activates the dependency-free `secrets` capability and publishes the
storage boundary under `base64_ng::secret`. This checkpoint defines ownership,
redaction, cleanup, exposure, and declassification. Commit 19 now composes
these owners with the bounded decoder in `2.0_SECRET_DECODING.md`; secret
encoding now composes them with the bounded encoder in
`2.0_SECRET_ENCODING.md`.

## Type Boundary

The canonical storage types are:

- `SecretInput<'a>` classifies caller-owned input without taking cleanup
  responsibility;
- `SecretOutput<'a>` owns cleanup of a complete mutable borrowed range;
- `SecretArray<CAP>` owns fixed-capacity secret storage;
- `SecretVec`, with `alloc`, owns initialized bytes and allocation spare
  capacity;
- `ExposedSecret` and `ExposedSecretMut` are explicit interoperability views;
  and
- `DeclassifiedOutput` and `DeclassifiedArray` are ordinary, non-wiping values
  produced only by a visible consuming declassification operation.

Secret owners and classified input implement no `AsRef`, `AsMut`, or `Deref`
coercion. They are non-Clone. Passing one to an ordinary codec therefore
requires a visible `expose_secret` or `expose_secret_mut` call. Only explicitly
exposed views implement ordinary slice interoperability traits.

The `Base64Secret` derive follows the same rule: generated key types expose
bytes through `expose_secret` and `expose_secret_mut`, do not implement
`AsRef<[u8]>`, and redact both `Debug` and `Display`. Commit 42 owns the later
full derive migration to the final 2.0 secret codec types.

## Cleanup Ownership

`SecretOutput::from_initialized` wipes unused tail bytes before returning. An
invalid initialized length wipes the complete caller range before returning an
error. `clear`, ordinary unwinding, and `Drop` wipe the complete range.

`SecretArray` applies the same full-capacity policy. `SecretVec` wipes both its
initialized bytes and spare allocation capacity when it takes ownership,
clears, or drops. `SecretVec::replace_from_vec` wipes the displaced initialized
bytes and spare capacity before releasing that allocation, and wipes incoming
spare capacity before adoption. These are best-effort software wipes through
the crate's reviewed cleanup boundary; the limitations in `UNSAFE.md` still
apply.

`SecretInput` cannot wipe its immutable borrowed input because the caller owns
that storage. `ExposedSecret` and `ExposedSecretMut` are views whose originating
owner retains cleanup responsibility.

Cleanup destructors do not run after `mem::forget`, process termination, OOM
abort, or `panic=abort`. Panic cleanup applies only when Rust unwinds. They
also cannot remove historical copies from
registers, caches, compiler temporaries, swap, hibernation, snapshots, or crash
dumps. High-assurance deployments still require platform memory controls.

## Declassification

`SecretOutput::declassify` and `SecretArray::declassify` consume their secret
owner and return an ordinary non-wiping value. `SecretVec` uses the deliberately
long name `declassify_into_unprotected_vec`. These calls transfer cleanup
responsibility to the caller and are marked `must_use`.

Declassification is not a cleanup operation. It preserves the initialized
prefix and returns zeroed unused capacity where the source owner controlled
that capacity. The returned ordinary values may be copied, formatted, logged,
or dropped without wiping; callers must treat that as an explicit policy
decision.

## Evidence

`scripts/check-2.0-secret-storage.sh` provides:

- compile-fail evidence that secret owners cannot pass implicitly into
  ordinary codecs or generic slice traits;
- compile-fail evidence that secret owners and generated secret newtypes are
  not Clone;
- redacted `Debug` and `Display` tests for every secret and exposed wrapper;
- rejection, drop, and unwind cleanup tests for borrowed ranges;
- fixed-array tail, clear, drop-policy, and declassification tests; and
- heap-vector initialized-byte and spare-capacity cleanup tests; and
- allocation replacement cleanup through the same complete-vector boundary.

The public API snapshot records these types only when the `secrets` capability
is enabled. Ordinary type layout and behavior remain unchanged when Cargo
feature unification enables this separate capability.
