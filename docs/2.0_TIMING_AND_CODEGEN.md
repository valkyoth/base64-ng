# 2.0 Timing and Generated-Code Evidence

This document defines the evidence boundary for the constant-time-oriented
parts of `base64-ng` 2.0. It is deliberately narrower than a claim that a Rust
API, process, or machine is cryptographically constant-time. Base64 is not
cryptography, but decoded and encoded values can still be secret.

## Reviewed Surfaces

The reviewed scalar surfaces are:

- equal-public-length comparison through the sealed `SubtleSecretEq` boundary;
- bounded secret decode symbol mapping and validity accumulation;
- built-in and custom-alphabet bounded secret encode mapping;
- the opaque decode result gate;
- logical-range cleanup through `wipe_bytes` and `wipe_barrier`.

Ordinary strict, streaming, web-forgiving, profile, and SIMD APIs are outside
this claim. Secret paths must remain scalar and must not enter ordinary backend
dispatch.

## Fixed-work pre-result-gate boundary

For a fixed public frame size, alphabet, padding policy, and caller capacity,
the reviewed secret decoder scans every input position and every 64-symbol
custom alphabet without secret-indexed tables or content-dependent exits. It
accumulates malformed state before calling the non-inlined result gate. The
secret encoder uses arithmetic mapping for built-in alphabets and a fixed
64-entry scan for custom alphabets. Equal-length comparison scans the complete
public length.

The dudect-style equal-work cases cover:

- different valid contents;
- malformed position and malformed byte class;
- valid versus malformed input measured before the result gate;
- built-in and custom-alphabet encode contents;
- equality contents and first-versus-last mismatch positions.

These measurements are empirical evidence for one binary and machine. Source
pattern gates and generated assembly add review evidence but do not turn the
implementation into a formal constant-time proof.

## Success-only post-result-gate boundary

Successful decode performs a documented public declassification copy after
the result gate. Malformed decode returns an opaque error and performs no such
release. The evidence does not prove valid/invalid whole-call timing equality.
Applications that require indistinguishable protocol behavior after
validation must add their own dummy work, response normalization, and traffic
controls.

Input length, frame size, output capacity, selected alphabet/profile, padding
policy, final result, and released output length are public. The timing harness
records decode, encode, and equality public-length scaling as informational
comparisons; those classes are not subject to an equal-work threshold.

## Cleanup Evidence Binding

Generated cleanup evidence is bound to all of the following:

- source commit and clean worktree state;
- `Cargo.lock` checksum;
- exact `rustc`, target, feature mode, release profile, and LTO flags;
- the selected target barrier description;
- `WIPE_PRIMITIVE_REVISION` in `src/cleanup.rs`;
- the runtime wipe generation carried by the operation report and assurance
  token.

The static manifest records the primitive revision. It cannot infer the
runtime wipe generation for a particular operation; that value must come from
the operation report used to establish `WipedAttested`. Changing the overwrite
loop, barrier, or ordering semantics requires incrementing the primitive
revision and regenerating evidence.

The wipe claim is limited to volatile overwrite of the logical byte range and
the generated barrier sequence. It does not prove erasure of registers,
caches, allocator history, swap, snapshots, historical copies, or
compiler-created copies. It also does not cover caller-owned input or data
copied by surrounding applications.

## Target Evidence

Run host evidence with:

```sh
scripts/generate_ct_asm_evidence.sh
BASE64_NG_RUN_DUDECT=1 scripts/check_dudect.sh
```

Generate assembly for an installed target with:

```sh
BASE64_NG_CT_ASM_TARGET=aarch64-unknown-linux-gnu \
  scripts/generate_ct_asm_evidence.sh
```

Host artifacts are written under `target/release-evidence/asm/`; explicit
target artifacts are written under `target/release-evidence/asm/<target>/`.
Timing artifacts are written under `target/release-evidence/dudect/`.

Evidence must be classified accurately:

| Evidence | What it supports |
| --- | --- |
| Native release/LTO assembly | Generated-code review for that compiler, flags, and target |
| Native timing on idle hardware | Empirical distributions for that binary, CPU, OS, and run |
| Cross-compiled assembly | Target code-generation review only |
| QEMU execution | Functional/emulated execution, not native timing or microarchitecture |
| Wasm module/codegen checks | Rust-to-Wasm code generation, not downstream JIT behavior |
| Browser/runtime smoke | Functional execution in the named runtime, not a stable JIT timing claim |

The target barrier posture is target-specific. x86 uses reviewed fence
instructions; AArch64 effectiveness can require operator CSDB attestation;
RISC-V has an ordering fence rather than a universal speculation barrier; and
Wasm remains compiler-fence-only with downstream JIT behavior outside the
crate's control.

## Required Symbols

Release and fat-LTO artifacts must retain concrete, non-inlined definitions
for:

- `wipe_bytes` and `wipe_barrier`;
- `constant_time_eq_public_len` and `ct_accumulate_u8`;
- `ct_error_gate_barrier`;
- `secret_encode_ascii` and `secret_encode_scan`;
- the bounded secret decoder `decode_symbol` boundary.

Reviewers must inspect the generated bodies, not only symbol presence. The
automated symbol gate protects the review boundary from disappearing through
inlining; it does not prove the body is branchless or constant-time.

## Residual Limitations

Rust and LLVM do not provide a contractual constant-time guarantee for these
ordinary source constructs. `black_box`, volatile operations, non-inlining,
compiler fences, and architecture fences are evidence-oriented mitigations,
not a language-level proof. Compiler upgrades, optimization changes, CPU
microarchitecture, speculative execution, caches, interrupts, scheduling,
frequency scaling, virtualization, and runtime JITs can alter observations.

For every release candidate and every target included in a timing claim:

1. Regenerate release and LTO assembly from a clean source tree.
2. Review every required symbol and archive the manifest and checksums.
3. Run equal-work timing campaigns on representative native hardware.
4. Record public-length comparisons separately as expected scaling evidence.
5. Re-run after any compiler, flags, target-feature, barrier, or wipe revision
   change.
6. Obtain an independent side-channel and compiler-assumption review.

No formally verified cryptographic constant-time guarantee is claimed.
