# 2.0 Constant-Time-Oriented Secret Encoding

Status: Implemented by Commit 20 under the dependency-free `secrets` feature.

Secret encoding is not ordinary encoding placed in a redacted wrapper. The
secret encoder has its own bounded scalar state machine, mapping functions,
storage owners, cleanup behavior, and evidence gates. It remains described as
constant-time-oriented rather than formally constant-time.

## Computation Boundary

Built-in alphabets use private arithmetic mapping. Standard and URL-safe
symbols are selected with byte masks; the secret six-bit value is never used
as a table index.

Custom alphabets use one fixed 64-entry scan per output symbol. The loop index
is public, every candidate is visited, and a mask accumulates the selected
byte. A validated alphabet supplies immutable data only, never executable
mapping behavior.

Encoding has no malformed secret-content class: every byte string is
encodable. Codec decode-acceptance settings therefore do not affect secret
encode eligibility. The validated alphabet and encode-padding policy fully
determine the output.

The built-in arithmetic mapper is private and exhaustively compared with both
the ordinary mapping and an independent RFC 4648 oracle for all 64 values.
Custom mapping is compared with the same oracle and records exactly 64
candidate visits per emitted symbol in deterministic tests.

## Frames And Storage

The public owners are:

- `SecretArrayEncoder<CAP>` for fixed stack-backed encoded capacity;
- `SecretEncoder<'a>` for caller-provided protected output;
- `SecretVecEncoder` with `alloc`, preallocated to the complete public bound;
- `Base64::encode_secret_array`, `Base64::encode_secret_into`, and
  `Base64::encode_secret_vec` for one-shot use.

`SecretArrayEncoder<CAP>` enforces `CAP <= MAX_SECRET_STACK_ENCODED` (1,368
bytes), which is the padded RFC 4648 output bound for the 1,024-byte decoded
stack policy. Larger frames use caller-controlled protected storage through
`SecretEncoder` or preallocated heap storage through `SecretVecEncoder`.

Every constructor accepts or derives a public maximum input length. The exact
maximum encoded length is checked before classified bytes are accepted.
No secret frame reallocates after accepting input. Incremental updates accept
only `SecretInput` and write only into storage whose owner wipes the complete
range on error, unwinding, or drop.

Encoded secret output remains secret until explicit exposure or declassification.
Ordinary formatters and counted sinks do not accept `SecretInput`.
A caller must first finish the frame, then deliberately expose or declassify
the resulting secret owner before sending encoded bytes to an irreversible
sink.

Input and output ranges must be byte-disjoint. Address arithmetic is checked,
overlap latches an absorbing failure, and the complete output range is wiped.
An input-limit or internal output failure has the same absorbing cleanup
posture. Successful finalization wipes unused output capacity and the private
two-byte input tail.

## Examples

```rust
use base64_ng::{STRICT_STANDARD_PADDED, secret::SecretInput};

let input = SecretInput::new(b"secret");
let encoded = STRICT_STANDARD_PADDED
    .encode_secret_array::<8>(&input)
    .unwrap();

assert_eq!(encoded.expose_secret().as_bytes(), b"c2VjcmV0");
```

Incremental output remains secret until a visible declassification step:

```rust
use base64_ng::{STRICT_STANDARD_PADDED, secret::{SecretArrayEncoder, SecretInput}};

let mut frame = SecretArrayEncoder::<8>::new(&STRICT_STANDARD_PADDED, 6).unwrap();
frame.update(&SecretInput::new(b"sec")).unwrap();
frame.update(&SecretInput::new(b"ret")).unwrap();
let ordinary = frame.finish().unwrap().declassify();

assert_eq!(ordinary.as_bytes(), b"c2VjcmV0");
```

## Evidence And Limits

Run the deterministic and compile-fail checkpoint with:

```sh
scripts/check-2.0-secret-encoder.sh
```

The release evidence also includes:

- release and fat-LTO assembly for `secret_encode_ascii` and
  `secret_encode_scan` through `scripts/generate_ct_asm_evidence.sh`;
- built-in-content and custom-alphabet dudect-style timing classes;
- bounded Kani proofs for final-quantum output bounds, absorbing oversized-input
  failure, and overlap/address-range preflight;
- exhaustive one-shot and incremental tests over lengths, chunk boundaries,
  all strict padding policies, custom alphabets, cleanup, overlap, and unwind;
  and
- compile-fail evidence that classified input cannot enter ordinary
  incremental or formatting surfaces implicitly.

These controls do not prove constant execution time on every compiler, target,
CPU, or runtime. Cleanup cannot erase historical register, cache, swap,
snapshot, or crash-dump copies. High-assurance deployments must retain the
platform controls and exact-toolchain review described in `CONSTANT_TIME.md`
and `UNSAFE.md`.
