# 2.0 Codec Specifications

Status: Public through the Commit 17 profile and terminology surface.

Commit 6 defined the complete internal policy value. Commit 12 publishes the
sealed trait, validated settings, builders, strict presets, and canonical
one-shot/incremental operations while preserving every frozen 1.3.9 API item.

## Model

`Base64<S>` has one specification type parameter. It does not encode alphabet,
padding, canonicality, backend, wrapping, or secrecy as separate generic
parameters. One sealed `Codec` trait returns a complete immutable
`CodecSettings` value containing:

- one owned `ValidatedAlphabet`;
- the encode-padding policy;
- the ordinary decode-padding policy; and
- the unused trailing-bit policy.

The trait is object-safe and requires `Send + Sync`. Later generic hot paths
monomorphize over one whole specification type. Integration boundaries may use
`dyn Codec` without changing policy semantics. The trait has no associated
constants because owned runtime specifications and trait objects must follow
the same contract.

Const transforms do not require const trait dispatch, which stable Rust does
not provide for this object-safe trait. Each built-in or runtime `Base64`
value instead exposes immutable `const_settings` and concrete const array
methods that operate on the same validated `CodecSettings` value.

Strict built-ins are zero-sized marker specifications and can be used in const
codec values. A runtime codec owns its 64-byte alphabet and policy enums inline:
there is no allocation, callback, borrow of caller memory, or `std` dependency.
The current size check caps the runtime codec at 72 bytes; exact layout is not a
stable consumer contract.

## Strict Presets

The four first-class strict presets are:

- RFC 4648 Standard with required canonical padding;
- RFC 4648 Standard with forbidden padding;
- RFC 4648 URL-safe with required canonical padding; and
- RFC 4648 URL-safe with forbidden padding.

All four reject noncanonical trailing bits, whitespace, mixed alphabets,
impossible lengths, malformed padding counts and positions, and trailing data.
They are traced to the locked RFC 4648 vectors and retain the behavior of the
matching 1.x strict engine. Later public aliases forward to these values rather
than defining separate behavior.

The locked requirement trace is:

| RFC 4648 ledger requirements | Commit 6 decision and evidence |
|---|---|
| `3.1`, `3.3`, `3.4` | Strict presets reject every ASCII whitespace byte at every short-vector position, all non-alphabet bytes, early/excess padding, mixed alphabets, and glyph/case substitution. |
| `3.2`, `4-PADDING-CASES`, `5-EXPLICIT-PADDING-OMISSION` | Padded presets require canonical padding; explicitly unpadded presets forbid it. Short padding counts and positions are exhausted. |
| `3.5` | Strict presets require zero unused trailing bits; every possible trailing six-bit value is exhausted for one- and two-byte tails. |
| `4-24-TO-4X6`, `4-STANDARD-ALPHABET`, `5-URL-SAFE-ALPHABET` | The single validated table drives both mappings and the four presets match Section 10 vectors plus Standard/URL-safe mixed-symbol rejection. |
| `5-DISTINCT-NAME` | URL-safe strict marker and preset names remain distinct from Standard. |

## Advanced Builder

`CodecBuilder` starts from an already validated alphabet or validates an owned
array/slice. It sets encode padding, decode padding, and trailing-bit handling
independently. `build` rejects the two self-inconsistent combinations:

- padded encoding with decode padding forbidden; and
- unpadded encoding with canonical padding required.

The accepted ordinary decode modes are required canonical padding, forbidden
padding, and explicitly padding-indifferent input. Matching `base64` `0.23.0`,
the indifferent mode accepts canonical padding, absent padding, or fewer than
the canonical number of padding bytes; strict presets never use it. Trailing
bits either remain canonical or use an explicitly named mode that allows
noncanonical trailing bits. These modes match the compatible configuration
semantics of exact-pinned `base64` `0.23.0` in repository-only differential
tests.

Padding-indifferent decoding and noncanonical trailing bits never qualify for
secret decode. A runtime custom alphabet may qualify for secret decode only
when its decode padding is required or forbidden and its trailing bits remain
canonical. Secret encoding depends only on the validated alphabet and encode
padding because every byte string is encodable. Commit 20 supplies its separate
fixed-work mapping and storage contract.

Commit 16 exposes every accepted relaxed combination as an explicitly named
constant in `compat`. These remain ordinary `Base64<RuntimeSpec>` values and
are distinct from the exact WHATWG algorithm under `web::FORGIVING`.

Commit 17 adds accurately scoped ordinary presets for MIME/PEM body layout and
bcrypt, `crypt(3)`, PBKDF2, BinHex, and IMAP modified-UTF-7 alphabets. These do
not add container or password-record semantics. See
`2.0_PROFILES_AND_TERMINOLOGY.md` for the exact boundaries.

## Evidence

`scripts/check-2.0-specifications.sh` verifies:

- valid const built-in and runtime codec construction;
- compile failure for third-party `Codec` implementations;
- compile failure for direct settings mutation;
- all twelve policy combinations, including all four rejected combinations;
- object safety, `Send`, `Sync`, marker size, and bounded runtime size;
- RFC 4648 Section 10 vectors through matching strict 1.x behavior;
- malformed strict cases covering whitespace, alphabet mixing, padding,
  lengths, trailing data, and unused trailing bits; and
- accepted advanced policies against exact-pinned `base64` `0.23.0`.

Run the checkpoint on the active toolchain and MSRV with:

```sh
scripts/check-2.0-specifications.sh
BASE64_NG_SPECIFICATION_TOOLCHAIN=1.90.0 \
  scripts/check-2.0-specifications.sh
```
