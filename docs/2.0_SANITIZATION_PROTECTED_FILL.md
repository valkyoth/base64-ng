# 2.0 Sanitization Protected Fill

Commit 40 gives the optional `base64-ng-sanitization` companion a 2.0-native
secret decode boundary. It does not merge two independent protected-memory
ownership systems or overstate what either one can prove.

## Two Reviewed Paths

`Base64::decode_assured` is the core single-allocation route. Its
`ProtectedSecret<Uninitialized>` allocation becomes internally `Unvalidated`
and is exposed only as `ProtectedSecret<Validated>` after the fixed-work result
gate. The exact provider owns reservation, stable range, generation checks,
quarantine, and ordered fallible teardown. No post-decode plaintext copy is
performed.

`SanitizationProtectedDecodeExt` is the companion route for applications that
already admit `sanitization`. It creates separate protected staging and final
mappings under the required memory-lock, dump-exclusion, and fork-exclusion
request. Decoder work starts only after both mappings exist. `SecretFrame`
keeps output behind its result gate, wipes both mappings on failure, and only
the initialized final mapping is returned.

The companion cannot treat a `sanitization` mapping as a core assurance
provider allocation. `sanitization` deliberately does not export the raw
ownership, address, generation, page-accounting, or teardown hooks required by
`ProtectedMemoryProvider`. Consequently:

- core quarantine and recovery claims apply only to `decode_assured`;
- the companion relies on `sanitization`'s protected constructor, integrity
  checks, wipe, unlock, and unmap behavior;
- a generic assurance token never proves that a `sanitization` allocation is
  protected;
- all companion protected-fill operations are out-of-place; encoded input,
  staging, and destination are distinct logical ranges.

## Fixed And Dynamic Allocation

`decode_sanitization_protected_bytes::<N>` allocates two fixed `N`-byte
mappings. It requires an exact decoded length of `N`.

`decode_sanitization_protected_vec::<MAX>` allocates two `MAX`-byte mappings
before decoder work. `MAX` is public application policy. Allocation shape is
therefore independent of frame validity after input delivery, and the final
mapping records only the validated initialized prefix.

Neither API calls the ordinary decoder or computes validity with an
early-return alphabet lookup. Both route through the same fixed-work
`SecretFrame` used by the core secret API. Errors retain only allocation class,
protection/integrity class, public lengths, or the opaque secret decoder error.

## Cleanup Ownership

Before the result gate, upstream protected constructors own both mappings and
remain armed on errors and unwinding. The destination is transferred only
after successful initialization and integrity verification. Staging remains
owned until it is cleared and dropped. There is no safe byte-access API for an
unvalidated companion destination.

Process abort, disabled unwinding, power loss, hostile kernel behavior, and
historical copies outside these owned mappings remain outside destructor-based
cleanup guarantees. See `docs/2.0_ASSURANCE_AND_PROTECTED_MEMORY.md` for the
stronger provider protocol and its explicit residual risks.
